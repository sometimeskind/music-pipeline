# Classify a library problem

Find the facts yourself before proposing a fix. The structured reads (`library_status`,
`find_albums`, `get_album`, `get_item`, `get_playlist`, `list_quarantine`) and the audits
answer most questions. Most `[TAG]`s below are also recorded as events: `album_history` shows
an album's, and `digest_summary` the last day's. The full log lines are in Loki: a Claude Code
session can read them through the Grafana MCP, and from claude.ai ask the user to paste them. A
job's own output is returned by the tool and by `get_job`.

Each audit's last lines say what it compared and what it left out. A clean result covers only
what it compared: `audit_grabs` at 0 of 1,208 says nothing about an album just reset to `wanted`.

More than one row can apply. A reimport that ends `[DONE]` and moves old copies aside also
creates new only copies.

| Symptom | Look at | Fix |
|---------|---------|-----|
| Two copies of tracks on **one album** | `get_album` (its items and their `via`), the album's `[DONE]`, `[RETIRE]`, `[LOCAL]` lines | Usually nothing. The next scan retires `[LOCAL]` extras the release now holds by ID (`[RETIRE] … (extra, now held)`) and merges those whose audio a release track holds (`[RETIRE] … (extra, same audio)`). `[LOCAL] … left to music-audit-dupes`: `audit_dupes`, then `merge_items` for the pair. `[LOCAL] … one track with extra(s) …, and with none of the release's items`: two extras share an ID, often a recording one of them took wrongly at import (a live take and a studio track, homelab#2609); compare them with `get_item`, never merge them, and `set_recording` the wrong one (it aligns the recording's ISRC, release track and artist fields, `artist*`, `mb_artistid(s)` and any arrangers or remixers the item held, and shows each in the dry run; re-running it on a recording the item already holds repairs artist fields a first run left). Another take still there after a scan: `reset_album` with `reimport=true` |
| **Path clashes** (digest "N path clashes", `[CLASH]` on a `NN - Title.1.m4a`) | the `clash` events in `digest_summary` or `album_history` (one a day per clash while it stands; each names its `item_id`); `get_album` | Seen once during a reimport: transient, nothing to do. One a day for several days: two items for one slot that no ID links. `audit_dupes`, then `merge_items` with `[keep, drop]` (same audio: keep the release's copy). The message names paths: take the other item's ID from `get_album` or the audit |
| The same song on **two albums** | import_alongside and kept_apart events (`find_events` by kind or `item_id`; `data.why` says why and `data.duplicate` names the other copy); `get_item` on each | `audit_dupes`, then `merge_items` for a pair the user confirms is one recording |
| Whether **two items are the same audio** (before a merge, or a copy with no fingerprint) | `compare_items` with the two item IDs | `[COMPARE]` gives the verdict and its evidence. `[NOFINGERPRINT]`: `fingerprint_items` on that item, dry run then apply, then `compare_items` again. An album's local-only extra that then matches a release track is merged by the next scan, so say so before the apply. `audit_dupes` compares only stored fingerprints between items sharing an artist word, and `recheck_recordings` skips an item with no `mb_trackid` |
| An album **mixed** from several releases | `audit_releases`, `[AUTORESET]`, `[MIXED]`, `list_overrides` with `kind=hold` | Nothing while the tick resets 3 a day automatically. Mixed on purpose (a hand-curated album): `hold_album` with the reason, and it stays mixed for good (`release_album` undoes it). By hand: `reset_album` with `reimport=true` for the album `audit_releases` names |
| **Only copies** in `quarantine/replaced/` (`MusicReplacedOnlyCopiesWaiting`) | `list_quarantine` with `kind=replaced`; `audit_releases` with `replaced_query='<artist — album>'` | The user decides per album. Deleting them (`--apply --only-copies`) is irreversible and runs on the workstation only (see `workflow`) |
| A **superseded copy to keep** in `quarantine/replaced/` (the only file of its take, though an item holds its recording by a wrong ID, so the purge deletes it 14 days after the move) | `list_quarantine` with `kind=replaced` and the item ID as `query`; `get_item` on the item that holds the recording | `keep_quarantined` with the file's path or its item-ID prefix: it moves to `quarantine/keep/`, which nothing purges (`list_quarantine` with `kind=keep`). Fix the holding item's recording too (`set_recording`), or the next import of that take is merged into it again |
| **Wrong release** imported (wrong edition, wrong album) | `get_album` (record, `blocklisted`), `[RELEASE]`/`[NOMB]`, `[DONE]`/`[WRONG]` | `reset_album` with `reimport=true`. A hand-curated album: `hold_album` instead |
| Album stuck `wanted` / `fallback` / `failed` | `get_album` (status, attempts), `album_history` (what was tried), `library_status`, `[MISS]`/`[FALLBACK]`/`[ERR]` | Fell back during an indexer outage: `requeue_albums` with `since`. A name of glyphs only (`[NOWORDS]`), or `[MISS]` with queries the indexer can't match, or whose closest result fails `album words`: `set_search_override` with words a release title holds (check them in the indexer's own search first, and with `check_release`). `failed`: `reset_album` |
| **Wrong take or length** (demo, radio edit, silence) | `audit_lengths` (`silence=true` for padding), `list_quarantine` with `kind=rejected` (album request fallbacks only: playlist downloads aren't checked at import) | `replace_item` with the item ID and a YouTube video the user picked. A fingerprint mismatch `audit_dupes` reports is fixed the same way. Re-downloading through the inbox doesn't work: the duplicate hook merges it back into the old item |
| A **track never downloads** (`[MISS] … no source found` on every retry, e.g. a glyph-only title) | `get_playlist` (the entry, `item_id: null`), `list_overrides` with `kind=pin` | `pin_track` with the Spotify track ID and a source URL the user picked (a YouTube Music video): the nightly downloads it from there. The dry run says whether the library holds the track already; then the pin is skipped, and `replace_item` changes the item's audio instead. `unpin_track` once it is in |
| A track shows as **another version** in Navidrome (a 5.1 mix, a live take: its `mb_trackid` names a sibling recording) | `get_item` (`mb_trackid`); the replaced recordings in `digest_summary` | `recheck_recordings` with the item's ID (or none, for the whole library: about an hour), then `apply_recheck` with its `job_id` once the user has seen the replacements. Several recordings for one item are left alone: never pick one. The apply refreshes the item's `title` and `trackdisambig` from the new recording too; an item replaced but still titled or disambiguated as the old version (replaced before homelab#2544, or `[NOREFRESH]`) needs the operator's `music-mb-fingerprint --refresh-replaced` (workstation-only, see `workflow`). When AcoustID itself names the sibling (the recheck agrees with the wrong recording, or would replace the right one with it: a remaster and its 5.1 fold-down or live take fingerprint alike), `recording_candidates` with the item's ID: it lists the recording at the item's position on its release and the release's other recordings of the song, with lengths beside the file's (a `[VARIANT]` line means the item's files are another release of the group, whose recordings are listed too). Show them to the user, let them pick, then `set_recording` with that MBID; its dry run shows the recording beside the item and the ISRC and release track that go with it, and the apply marks the item so rechecks leave it alone. Never pick between siblings yourself |
| A track **titled as the wrong version** (*(5.1 mix)*, *(live)*, *(outtake)*, *(take 1)*, or a `trackdisambig` "live, …" on a studio track) | `audit_titles` (by album, each item with Spotify's title at its slot and the version word only ours names); `get_item` | The import wrote a sibling recording's title. `reset_album` with `reimport=true` for the album, after a dry run (the audit prints its reset command). The album is the unit: never retitle one track. Since homelab#2544 a Usenet album import keeps its files' own titles, so such a track is from an album imported before that, or a spotdl import (`get_item` shows `via`). Its `mb_trackid` may name the sibling too: the row above |
| A track **under another artist** (an album's track credited to someone its album artist shares nothing with, or filed under that artist's folder; a same-title song by someone else) | `audit_artists` (by album, each item with its artist, its album artist and its fix, then the count); `get_item`; the retitled events (`find_events`, `data.dropped_why` "another artist") | beets matched another artist's recording of the same title. `recording_candidates` with the item's ID, the user picks, then `set_recording`, which aligns the artist fields with the recording, by the names it credits, also on an item whose artist is only the file's own tag (run it again on an item already on the right recording, as 18518 is, and it repairs them). The fix is the item's, not the album's. The audit leaves out compilations and any album mostly by others; a guest or a soundtrack's song by someone else can still be listed, so check it with the user before changing it. Since homelab#2649 a Usenet album import refutes such a match and keeps the file's artist (`[TITLE] … (recording dropped: another artist, …)`), so a listed item is from before that, or a spotdl import (`get_item` shows `via`) |
| An album that is **another album by the artist** (an album name sharing a word with its artist: *Curtis Live!* holding *Live in Europe*) | `audit_grabs` (each album, the release it came from and what the title adds, then the count, and what it didn't compare, by status); `get_album` (`candidate.title`, `release_files.album`, its items) | The title held the album's words only through the artist's name. A listed album may be right, so check its tracks. Then `reset_album` with `reimport=true`, once the user agrees: the album's other releases are tried, and it stays as it is if Usenet has no copy. Since homelab#2656 the tick refuses such a title (`artist words`), so a listed album is from before that |
| An album whose **import found none of its wanted tracks** (`[DONE]` … `2 of its 2 wanted track(s) not in this release`: an album under 4 wanted tracks isn't judged by its titles, so a wrong album passes) | `audit_zero_wanted` (each album, the release it came from, then the count, and what it didn't read); `get_album` (`candidate.title`, its items); `get_playlist` | A listed album may be right: title formats can differ, and the wanted tracks may be another edition's, so check its tracks. Another album: `reset_album` with `reimport=true`, once the user agrees. The audit only reports. It can't see an import before 2026-10-29, nor a wrong album sharing one wanted track |
| **Missing cover** | `[NOART]`; `get_item` (`via`) | `embed_covers` (Usenet items). An album split in two, one without a cover: `canon_albums` |
| **Playlist drift** (the `.m3u` lacks or has extra tracks against Spotify) | `get_playlist` (entries with `item_id: null`), `[SLOT]`, `[STORE-TAIL]` | No tool: the store is the truth, and a Spotify edit reaches the `.m3u` at the next nightly. A lasting gap is an entry no item holds by Spotify ID or ISRC: get the track in (a download, `replace_item`, a Usenet album) |
| An **imported album's track is in the library but its playlist entry is empty** (`get_playlist`: `item_id: null`; `get_item`: no `spotify_ids`, `listed_on: []`) | `album_history`'s id_linked event (`skipped` says why), `[NOID]`, `[NUMBER]` | `backfill_album_ids`, dry run first: it links an entry to the release item at its disc and track with its title. `[NOID]` lines stay empty, each with its reason. When the reason is `number, other isrc` (clean against explicit: no tool can hear which it is) and the user says the file is the entry's version, `recording_candidates` lists the entry's recording, and `set_recording` gives the item its ISRC, which fills the entry. A track renumbered on the release stays empty the same way: a title alone never links |
| A **wrong extra** on an album: `[LOCAL]` items of a wrong release a reimport left behind, another recording than the release's (`get_item`: album_extra, often album_extra_twin naming the release item at its slot) | `get_album`; `get_item` on each (listed_on, `spotify_ids`, canon_clash on the release item an extra keeps off its path) | `retire_item` with the IDs and a reason, dry run first: their files go to `quarantine/replaced/retired/`, and the purge **deletes them 14 days later** (`keep_quarantined` rescues one). Not `merge_items`: no ID agrees. It refuses the whole call for a release's own track, a loose copy (no album_extra) and the last item a playlist entry resolves to; see `album-mode` for those |
| A playlist slot plays the **wrong song** (`get_playlist`'s `item_id` is another recording) | `get_item` on the slot's item (`spotify_ids`, `isrc`, `merged_files`) and on the right one; `find_albums` for it | The slot's item holds the entry's Spotify ID wrongly (often from a wrong merge: its `merged_files` names the entry's song), and an entry resolves by Spotify ID before ISRC. The right item in the library, holding the entry's ISRC: `unlink_spotify_id` with the wrong item's ID and the entry's `song_id`; its dry run says where each entry resolves afterwards. The wrong item holds the entry's ISRC too, or the ID is its `spotify_url`: it is a wrong download, so `replace_item`. Never unlink an ID from the right recording |
| Tick failing, not run, downloads stalled | `library_status`, the tick summary line | See `album-mode`. Mostly no tool: the cause is an indexer, SABnzbd or the egress, which are operator matters |
| Album never downloads | `get_album` (status, attempts, `blocklisted`); `audit_want_albums` | See `album-mode` |
| Would a release **match** an album, or would an **override** help | `check_release` with the album, the release title and any override `words`: accepted, or the rule that refused it | Nothing to guess: quote its verdict. See `album-mode` |

## What the MCP can't do

- **Playlist membership** (`playlists.conf`) stays a homelab PR: it is structural, and its
  flags grant Spotify writes. Search overrides, holds and pins are MCP tools (above).
- **Irreversible operations** (deleting only copies, a bare `music-audit-dupes --apply`,
  `--force`, `--quarantine`, `--allow-manual`, rollbacks) are workstation-only. See `workflow`.
- **Pod and egress problems** (SABnzbd paused, Prowlarr down, the Mullvad exit, YouTube
  cookies) are in homelab's runbooks.

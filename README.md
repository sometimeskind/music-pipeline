# music-pipeline

Dockerized music pipeline: Spotify playlists → spotdl downloads → beets import/tag → music library.

```
Spotify playlists → spotdl → beets → ~/Music/library
```

A single long-running service container orchestrates everything via Prefect. Two flows run on configurable schedules:

| Flow | Default schedule | Does |
|---|---|---|
| `music-fetch` | Daily 03:00 UTC (`FETCH_CRON`) | Spotify/YouTube sync — downloads new tracks, queues removals |
| `music-scan` | On demand (file watcher or HTTP API) | Import inbox → beets, refresh metadata, regenerate .m3u |

A scan that finds the `pipeline` lock held (a fetch, another scan or an album import) with an empty inbox skips after 5 seconds. When the inbox holds audio files it would import, it waits for the lock, up to 30 minutes (`[WAIT] Got the pipeline slot after Ns`), the way an album import does, so a stretch of chained album imports delays the inbox by about one import rather than until the stretch ends (homelab#2761). At most one scan waits: the waiter holds the one-slot `scan-wait` limit until it has `pipeline`, and a busy scan that finds `scan-wait` held exits (`Scan skipped — pipeline busy; another scan is already waiting for the slot (N file(s) waiting)`), since the waiter imports its files too. When the wait runs out, or `scan-wait` can't be taken, the scan schedules one more `music-scan` run 5 minutes on (`Scan skipped — pipeline busy; retrying in 5 min (N file(s) waiting)`), unless a scan is already scheduled or pending; the retry waits and falls back the same way, so the inbox always ends with a scan that ran (homelab#2751). Files still copying under a temporary name (`.partial`) don't count. Files already in the inbox when the service starts get the same treatment: once the file watcher runs, and after an interrupted album import has been moved back to SABnzbd's complete dir (`[RESUME]`), the service schedules one `music-scan` run 30 seconds on (`Startup: N file(s) waiting in the inbox; scheduled a scan`), unless a scan is already scheduled or pending. A Prefect server it can't reach then is logged, and the service starts anyway.

**A restart never loses an inbox or quarantine file (homelab#2763).** The SIGTERM that stops the pod reaches a running `beet import`, which stops early. The scan then ends there, as a crashed run pushed with `music_scan_last_failure_reason{reason="interrupted"}`: it logs `[INTERRUPTED] beet import cut short: N of M inbox file(s) stay in the inbox for the next scan, none quarantined`, and neither quarantines the inbox's leftovers nor starts the as-is pass, so the startup scan after the restart imports them. Before, beets stopping read as a finished import: the scan quarantined every file beets never reached and staged them for the as-is pass in the container's `/tmp`, and a restart lost 68 files. A `beet import` killed by any other signal, or exiting non-zero, fails the scan the same way, before the quarantine. An album import cut short leaves its job folder in the inbox, and the next start moves it back (`[RESUME]`, #344). The as-is pass stages in `asis-staging/` and `asis-apart/` beside `quarantine/`, on its volume, so a kill mid-pass leaves its files there; at start, before anything can scan, the service moves them back to quarantine (`[RESUME] N as-is file(s) back to quarantine`), and a file whose quarantine path has been taken meanwhile goes beside it as `<name> (restored).<ext>`.

## Pipeline internals

A full sync cycle (`music-ingest` followed by `music-scan`) runs 8 discrete steps. Steps 1–2 are the **fetch phase**; steps 3–8 are the **scan phase**.

```
┌─ FETCH PHASE (music-ingest) ──────────────────────────────────────────┐
│                                                                        │
│  [1] Playlist reconciliation                                           │
│        Reads playlists.conf; creates new playlists' inbox dirs, syncs  │
│        .nosync/.album sentinels, deletes the store and .m3u of a      │
│        playlist removed from config, then the Navidrome playlist       │
│        imported from any .m3u that is gone.                            │
│        │                                                               │
│        ▼                                                               │
│  [2] spotdl sync                                                       │
│        Fetches each playlist from Spotify, writes its playlist store   │
│        and downloads its want list (tracks no library item holds)     │
│        into inbox/. A track removed on Spotify leaves the store.      │
│                                                                        │
└────────────────────────────────────────┬───────────────────────────────┘
                                         │
┌─ SCAN PHASE (music-scan) ─────────────▼───────────────────────────────┐
│                                                                        │
│  [3] Pre-import checks (scan.PRE_IMPORT_STEPS)                         │
│        verify-request-downloads: length, silence and AcoustID checks   │
│        of album requests' fallback downloads; a match moves into the   │
│        inbox, the rest to quarantine/rejected/ (no re-download).       │
│        Playlist downloads are not checked (homelab#2579). The Prefect  │
│        music-scan flow and music-scan's run() both run this list.      │
│        │                                                               │
│        ▼                                                               │
│  [4] Beets import                                                      │
│        Matches inbox audio to MusicBrainz/AcoustID; moves matched      │
│        files to library/. Low-confidence matches go to quarantine/.    │
│        │                                                               │
│        ▼                                                               │
│  [5] Quarantine + asis pass                                            │
│        Moves unmatched inbox leftovers to quarantine/. Then attempts   │
│        a second beet import --asis for quarantine files that already   │
│        have sufficient embedded tags (title, artist, album, track#),   │
│        staged in asis-staging/ beside quarantine/ (homelab#2763).      │
│        Skipped when the import was cut short: its files stay in the    │
│        inbox.                                                          │
│        │                                                               │
│        ▼                                                               │
│  [6] Library metadata refresh                                          │
│        Runs beet update to refresh metadata on existing library items. │
│        │                                                               │
│        ▼                                                               │
│  [7] Playlist generation                                               │
│        Regenerates each .m3u from its playlist store (in Spotify       │
│        playlist order), resolving entries against the library.         │
│        │                                                               │
│        ▼                                                               │
│  [8] Navidrome trigger                                                 │
│        Calls the Navidrome Subsonic API to trigger a library rescan.   │
│                                                                        │
└────────────────────────────────────────────────────────────────────────┘
```

The scan phase is idempotent and safe to run at any time: on its 5-minute schedule with no preceding fetch it only imports what arrived and rewrites the `.m3u` files.

## State

The pipeline's own state is in the Postgres database `music` (`MUSIC_DATABASE_URL`, homelab#2410), read and written through one module, `music_fetch.state` (migration 4 in `music_fetch/db.py`; the overrides are migration 5 and `music_fetch.overrides`, the album requests migration 7 and `music_fetch.album_requests`, the Later queue migration 8 and `music_fetch.later_queue`):

| Table | Holds | Was |
|---|---|---|
| `albums`, `album_refs`, `album_playlists`, `indexer_use` | The album store: each album's status, release blocklist, Spotify snapshot per album playlist, fallback tracklist; the indexer budget | `inbox/spotdl/.albums.json` |
| `playlist_stores` | The playlist stores, one row per playlist | `inbox/spotdl/.store/<name>.json` |
| `spotdl_failures` | The spotdl backoff | `inbox/.spotdl-failures.json` (on the scratch volume, so a restore forgot it) |
| `kv` | The MusicBrainz release and ISRC caches (`mb-releases`, `canon-isrc`), the playlist-page cache (`canon-pages`), the Spotify rate-limit stamp, the empty-slots report, and the `state-imported` (historical) and `overrides-imported` markers | `.mb-releases.json`, `.canon-isrc.json`, `.canon-pages.json`, `.spotify-rate-limit.json`, `.empty-slots.json` |
| `album_overrides`, `track_pins` | Search overrides and holds (on an album row), track pins (by Spotify track ID), each with its reason, `set_by` and `set_at` (homelab#2484, see Album mode) | homelab's ConfigMap: `album-overrides.conf`, `track-pins.conf` |
| `album_requests` | Albums requested by MusicBrainz release group: the preferred release, the tracklist read from MusicBrainz, `requested_by` and `requested_at` (homelab#2478, see Album requests below) | new |
| `later_queue` | The Later queue: one row per album by release group, `added_at`, and `available_at` (when the library first held it whole; the `.m3u` order) (homelab#2478, see The Later queue below) | the `later` Spotify playlist, until the stage 3 cutover |
| `playlist_sync`, `playlist_sync_snapshot` | The two-way playlist sync's state (homelab#2361, migration 24): per playlist, the snapshot of its Navidrome playlist as `(item, song)` rows, the beets item and Navidrome's media file ID that held it (see Two-way playlist sync below) | new |

beets' library stays SQLite (`library.db`): beets has no other backend. The events (homelab#2413) are in the same database.

**Events, not logs, record the data (homelab#2590).** Every data-level change or decision (tags or paths written; an item imported, moved, merged, retired, quarantined or purged; an album record created, dropped or changed in status; a download accepted or rejected; a reset, hold or pin; a decision not to act that someone would ask "why didn't X happen?" about) is an event, read through the Music MCP's `album_history`, `find_events` (by kind across albums) and `digest_summary`. The log is for service-level debugging: run progress, counts, timings, errors, retries. A per-item line that repeats at every scan with nothing changed is DEBUG, its event (once a day where it stands) or the run's count line the report: `[CLASH]` (canon's `Changes` line counts them), `[LOCAL] … left to music-audit-dupes`, `[NOTWIN]` (the `Twins` line), and `[KEEP]` outside a dry run.

**Event kinds live in one registry (homelab#2618).** `fetch/music_fetch/event_kinds.py` lists every kind with its subject (album, item, playlist or none) and the `data` fields it carries; it is the full reference, and the paragraphs here and in `service/MCP_API.md` describe the events by area. Kinds are validated in code (`events.record` and `events.insert` refuse an unregistered one), not by the database: migration 23 dropped the `events_kind_check` CHECK, so a new kind is a registry entry, with no migration. `service/tests/test_event_kinds.py` reads every `events.record` and `events.insert` call and fails when one records an unregistered kind or spells out a `data` key its kind doesn't list. The events are an audit log of why the library changed, not event sourcing: nothing rebuilds state from them.

**The database is the only copy.** `music-state-import` moved the JSON dot files in on 2026-10-29 (homelab#2410). They were kept, unwritten, as a rollback copy behind a switch file (`inbox/spotdl/.state-in-db`) for one release; after it the JSON code, the switch and the import were removed and the files deleted (homelab#2502). A new piece of state is a migration and a `music_fetch.state` accessor, never a file. The tests run on Postgres too (CLAUDE.md, Testing).

**Album keys.** An album row is keyed by its MusicBrainz release group (homelab#2478). A row whose release group isn't known yet has none, and an `unresolved` flag says why: `pending` (not looked up), `no-match`, `conflict` (the evidence disagrees) or `in-flight` (a merge waits for an import to finish). Each of an album's Spotify album IDs, or a local album's `artist/name`, is a ref in `album_refs`, so two Spotify editions of one release group are one row. An override or hold is on the row itself, and follows it by ref through a merge (homelab#2484).

**The album key** is what album mode, the Music MCP and the `album_record` beets stamp on each imported item name an album by. It is the album's row id (homelab#2478): opaque, and the same before and after the album resolves to a release group, so resolving moves no stamp. Never read a key for what it is: a Spotify album ID is the record's `spotify_album_ids` (`state.primary_spotify`). Until the operator's one-time `music-album-rekey --apply` (the `album-keys` kv marker) the key is the old scheme, the primary Spotify album ID (else the release group, else the name), and a record not saved yet is keyed that way until its first save gives it a row.
- `music-album-rekey` (dry run unless `--apply`) lists the items whose stamp moves, per album. `--apply`, under the `albums` and `pipeline` locks, copies `library.db` to `library.db.pre-rekey-<UTC time>` beside it, writes the marker, then restamps every item (beets' database only, in one transaction). `--revert --apply` moves the stamps back to the old keys and then removes the marker: run it before rolling the image back to one from before homelab#2478, which reads stamps as Spotify album IDs.
- **A row that goes** (a merge's loser, an album that left its playlists) leaves its refs in `album_rows_gone`. Every scan, before its canon, moves a stamp naming a gone row (or an old key, or another edition's Spotify ID) to the record that holds one of its refs now (`[RESTAMP] artist — album: N item(s) old → new`, `music_scan.restamp`); a stamp no record claims is left as it is. Only once the keys are row ids: before that, the stamps are the operator's to move.

**The resolver** (`music_fetch.resolve`) keys the rows it can, every album tick and in `music-album-resolve` (dry run unless `--apply`). The first evidence that answers wins, never a fuzzy match:
1. the release group of the release album mode imported for the album (what is on disk); evidence that disagrees with it is reported;
2. the `mb-releases` cache's release for its Spotify album (by URL, ISRC or barcode, the canon lookups);
3. the beets items tagged with its Spotify album ID, when every one that has a release group has the same one.

Cache and library evidence that name two release groups leave the row `conflict`. Two rows that resolve to one release group merge (`[MERGE]`), never while either is grabbed or importing (they wait `in-flight`): the survivor is the row that already had the release group, else the one furthest along, and it takes the others' Spotify IDs, playlist tracks and blocklisted releases, the higher attempt count and the strongest origin. Each pass that changes anything logs `[MERGE]` lines and a `Resolve:` summary, which counts the rows flagged by reason; `[FLAG]`, `[REKEY]` and `[CONFLICT]` lines are listed with `music-album-resolve --verbose` (a conflict's text is in its daily event, below; homelab#2590).

**Album requests** (homelab#2478). `music-requests add [--apply] -- <release group>[=<preferred release>]…` (the Music MCP's `request_album`) asks for whole albums by MusicBrainz release group, each an MBID or a musicbrainz.org URL; `music-requests list [--status S]` (`list_requests`) shows each request with its album's status, `pending` until the tick has queued it. The dry run reads each tracklist from MusicBrainz: the preferred release's, else the earliest official release with the release group's most common track count (releases marked live left out, unless the group is a live album; video media left out), stored as album mode's track entries without Spotify IDs. Each album tick (`albums.feed_requests`, logged `[REQUESTS]`) gives every request an album row with origin `request` and those tracks under the pseudo-playlist `request`, or upgrades the row that has the release group: a waiting wants or library row becomes the request's (the whole album wanted), and an album playlist's row is marked `requested`, so it stays when it leaves its playlists and then takes the request's tracks. A playlist's Spotify tracks always stand in for the request's, so `have` and the import read one tracklist. A request is searched with the album playlists' albums, ahead of the fed ones, and imported under `inbox/usenet/request/`. When Usenet misses or all its releases fail, it falls back to spotdl from MusicBrainz (`albums.fallbacks`): the tick reads the request's tracklist release once (`album_requests.release_songs`, from the same 10 reads a tick as Spotify tracklists) as spotdl songs with every field set, so spotdl never asks Spotify. Each song's ID is its MusicBrainz recording and its URL `https://musicbrainz.org/recording/<id>`, with the release's Cover Art Archive front as its cover. spotdl finds it on YouTube Music by its ISRC, else by artists, title and length. Each credited artist is its own name in the song's artists (a track with no credit of its own takes the release's), and when that search finds nothing for a credit naming several artists, it is searched once more by the first credited artist alone, its ISRC already tried (homelab#2533, `[ALONE]`): spotdl joins every artist into its query and scores results by all of them, so a joint credit often finds nothing. Only the search widens: the song keeps its full credit and the same acceptance check. The nightly downloads the tracks no item stamped with the album's key holds into `unverified/request/`, outside the inbox, under the same budget and backoff. They come after every playlist, on what the playlists left of `SYNC_TRACK_LIMIT`: a night that spends it all, or reaches the soft timeout first, records a `fallback_deferred` event on each album with tracks still waiting (migration 14; at most one a day per album; `data.tracks`, `data.why`), so a request that stays in `fallback` with nothing downloaded says why in its `album_history` (homelab#2478). Before the import, the scan's `guard.verify_requests` checks each file: the length and silence checks (`guard.check_file`) against MusicBrainz's length, then an AcoustID lookup of its fingerprint (`ACOUSTID_APIKEY`). Only a file AcoustID names as the track's own recording (score 0.85 or more) moves to `inbox/spotdl/request/` (`[VERIFIED]`). Each verdict is an event (homelab#2590): `accepted` for a file moved on (a re-check's too, `data.recheck`), `reject`, and `held` for a file no longer re-checked. Every other file goes to `quarantine/rejected/request/` with its reason (`music_scan_rejected_tracks_total{reason}`): `duration` or `silence`; `fingerprint` when AcoustID names other recordings (or ours below 0.85), or the file can't be fingerprinted; `acoustid-unknown` when AcoustID has no MusicBrainz recording for the audio at all, no result or only results with no recording (homelab#2546). A `fingerprint` reject is the wrong audio; an `acoustid-unknown` one may be right, from a new or obscure release AcoustID hasn't linked yet, but it is rejected all the same. Its URL is then held, so it isn't downloaded again, and the track stays a gap. Rather than download it again, every scan re-checks the held `acoustid-unknown` files last looked up a day or more ago (`guard.recheck_unknown`, homelab#2546, the operator's call on 2026-11-01): AcoustID links new releases over time, and a lookup costs about a second. The rule is the same. AcoustID now names the track's own recording at 0.85 or more: the file moves to `inbox/spotdl/request/` and imports that scan (`[VERIFIED] … on re-check`). It names other recordings: the reason becomes `fingerprint` (`[REJECT] … on re-check`, a `reject` event), never asked again. Still nothing: it stays held. The `.reason` sidecar records `held:` and `checked:` times (UTC) after its first line; a failed lookup changes nothing and ends that scan's pass. After `ACOUSTID_RECHECK_DAYS` (default 30) held, a file is no longer re-checked (`stopped:`, logged once as `[UNKNOWN] … no longer re-checked`) and stays held for the operator: nothing purges `quarantine/rejected/`. Each scan logs its re-check counts (`AcoustID re-check of held unknown downloads: …`), and `fallback_rejected` follows them. A failed lookup (an AcoustID error, or no answer in 30s) is neither: it leaves the file for the next scan. The beets plugin records the verified recording as `fallback_recording` (and `mb_trackid` when beets set none), never as a Spotify field. A copy the library already holds of that recording doesn't stop it importing (`[BOTH]`), since the album keeps its own copies. Before canon, every scan stamps such an item with its request's key (`release.claim_fallback`, `[CLAIM]`). Canon names a request's items from MusicBrainz: album, album artist and date from the record, `mb_albumid`/`mb_releasegroupid`/`mb_albumartistid` from the tracklist release (`mb_album_via=request`), or from the files' own release for a Usenet import (`files`), and a fallback track's disc/track from the tracklist. They are one album with no `spotify_album_id`. The album's items (those stamped with its key, and those on one of its Spotify albums) hold a track by `fallback_recording` or `mb_trackid`, never by position: an edition numbers its tracks otherwise (key 162's item 61, *Such a Bad Way*, is track 5 of 10 on its Spotify album and 6 of 11 on the tracklist). An item beets matched to no recording has no `mb_trackid` (about a third of the library, mostly spotdl downloads from before requests), so it counted as missing and the fallback would download it again (homelab#2589). So while a request lacks a track, the album tick looks each of its items without a recording ID up on AcoustID (`music_scan.request_fill`; `ACOUSTID_APIKEY`). When exactly one of the tracklist's recordings is among those AcoustID links to its audio at 0.85 or more, and that track's title is the item's song, the item's `mb_trackid` becomes that recording under the pipeline lock, with a `recording_filled` event (migration 18; `data.key`, `data.new`, `data.score`, `data.track` the tracklist's position and `data.item_track` the item's) in the same transaction, and the file's tags are written (`[HELD] <artist> — <album>: <id> — <title> is the request's track N by AcoustID (<score>); mb_trackid → <recording>`). The held check then counts it, and so do `audit_dupes` and Navidrome, which identifies a track by its `mb_trackid` (so such an item may show there as a new track). A track title naming another song is `[SUSPECT]` and left alone; AcoustID naming none, or several, of the tracklist's recordings is `[NOFILL]`, and that item isn't asked about again until the pod restarts or its file changes. A failed lookup ends the tick's lookups and leaves everything for the next tick. `find_events` with kind `recording_filled`, or the album's `album_history`, lists the fills. The album is `filled` once its stamped items hold every recording, and until then `list_requests` shows `fallback_left` and `digest_summary` lists it under `requests.fallback`. Both also show `fallback_rejected`, the tracks left whose download is held in `quarantine/rejected/request/`, by reason (read from each file's `.reason` sidecar), and `acoustid_unknown_only` when every one of them is `acoustid-unknown`: the operator decides what such an album needs (Usenet only, a manual source, or a later retry once AcoustID knows the release). Rejects from before homelab#2546 all read `fingerprint`. While it has gaps it is searched on Usenet again every 7 days (`MISSING_RETRY`, as a miss is; it stays `fallback` on a miss). A release grabbed then is the album, and retires the spotdl copies whose recordings it holds. `music-requests fallback-sample [--n=10] [--seed=0]` (exec, an operator step) measures the hit rate: it runs these steps on N albums the library holds whole into a scratch directory and keeps nothing. Per album and in total, it reports the tracks spotdl found and the ones AcoustID accepted or rejected (by reason, `fingerprint` and `acoustid-unknown` apart), and how many of each match the library's own copy by fingerprint, the `acoustid-unknown` rejects on their own too. Before this fallback, a request that missed stayed `missing` (searched again weekly). Rolling back to an image from before migration 7 leaves the request rows alone, but that image would treat a request row as an album playlist's and fall it back to spotdl with no tracks to fetch, marking it `filled`: reset those albums after rolling forward again.

`music-requests search [--limit=N] -- <query>` (`search_releases`) finds the release group to request: it sends the typed query to MusicBrainz's release-group search as given (never a library title from an agent), and lists the best N matches (default 5, at most 10), each with its types, year and releases (date, country, media, track count), flagging live, remix, compilation, demo, DJ-mix and mixtape release groups and releases that are not official or whose disambiguation says live, demo, remix or compilation.

**The Later queue** (homelab#2478). `music-requests add --later` (`request_album` with `later`) also appends the albums to Later, in the order given; an album requested already is only appended. `music-later list` (`get_later`) shows the queue, and `music-later remove [--apply] [--through=N] [--album=<album>]… -- <release group>…` (`remove_from_later`) takes albums off it, by release group, by album (`--album`, as `music-overrides` names one: its key, a Spotify album ID or URL, or `artist — album`; a query matching several albums is refused and lists them; homelab#2534) or Later's first N; their files stay in the library. An album's `available_at` is set when it is added if the library holds it whole (its row `have`, `imported` or `filled`), else by the first `.m3u` regen that finds it so (`[LATER] N album(s) now held whole`), which follows its import. A reset or reimport doesn't move it. `later.m3u` lists the available albums in `available_at` order, each album's stamped release (`album_record`, found without a Spotify album for a request's row) in disc/track order, so an album that arrives late joins the end. Pending albums aren't in it. The queue alone writes `later.m3u`: a playlist store named `later` is not read for it (the album playlist left `playlists.conf` at the stage 3 cutover). When the queue can't be read, `later.m3u` keeps its last content. Rolling back to an image from before migration 8 leaves the queue's rows alone and drops the queue's albums from `later.m3u` until rolling forward again. An image from before migration 9 leaves the entries queued by ref out of `later.m3u` (it logs each as having no album row).

**Automatic requests for Later** (homelab#2535, `music_fetch.later_requests`). Since the cutover `later` is no album playlist, so spotdl gets no fallback for its albums, and the MusicBrainz-built fallback covers requests only. Each album tick in `on` therefore first requests every Later album that isn't held whole (its row not `have`, `imported` or `filled`), has a release group and has no request yet, in queue order and at most 5 a tick (two or three MusicBrainz reads each): an ordinary request with `requested_by` `auto:later`, logged `[LATER] … requested automatically` and recorded as its `album_requested` event, which the same tick then feeds. Both tables are unique on release group, so an album is requested once: a partial fallback stays `fallback` and is searched again weekly, never requested again, and leaving Later doesn't withdraw the request. An entry queued by ref waits until a regen gives it its row's release group. A release group MusicBrainz gives no tracklist for is skipped for 7 days, each refusal a `failure` event (`data.what` `later_request`); a MusicBrainz outage stops the tick's requests until the next tick. One `[LATER-REQ]` line a tick counts them (`dry-run` mode only counts). `music-later auto-requests` lists what the next tick would request, read-only and without MusicBrainz. A request's row that is not held whole drops the tracks of playlists that left `playlists.conf` (the former `later` and `keep` rows' Spotify tracklists, which spotdl no longer reads), so the request's MusicBrainz tracklist and fallback take over (`[REQUESTS] … off later, which left playlists.conf`); a held row keeps its Spotify tracklist.

**The cutover** (homelab#2478 stage 3). `music-cutover` (dry run unless `--apply`) moves Later and Keep off Spotify once, while `later` and `keep` are still in `playlists.conf`: it reads their stores. Every album on the `later` store goes on the Later queue in the store's order, each a second before the next and before every entry the queue has, so it keeps its place ahead of the albums requested since; one on the queue already moves to its store place. Every album on the `keep` store becomes a request, its tracklist read from MusicBrainz by release group at `--apply` (one MusicBrainz can't answer for is listed as `[SKIP]`: run `--apply` again). An album whose row has no release group yet is listed (`[NO-RG]`): on Later it is queued in its place by its album ref instead (migration 9: `later_queue.ref`, its primary Spotify album ID, which follows the album through a merge), and each regen gives such an entry its row's release group once the row has one (`[LATER] … resolved to release group`; an entry the album has by release group already, from a request with `later` meanwhile, is merged into the earlier of the two). Until then `music-later remove` reaches it by `--album` or `--through`, not by release group. A Keep album with no release group gets no request, and its row stays as it is until the album tick settles it (below, homelab#2602). A store album no row holds is listed (`[NO-ROW]`) and left out. The dry run renders `later.m3u` as the queue will write it and compares it with the file the last scan wrote: `later.m3u: unchanged by the cutover` is what to expect. `--apply` writes the queue entries (`later_added`, source `cutover`), the requests (`requested_by` `cutover:keep`) and the `later-keep-cutover` kv marker in one transaction, under the `albums` and `pipeline` locks; run again, it adds only what is missing. Then both lines leave `playlists.conf`, and the queue alone writes `later.m3u`. `music-cutover --revert --apply` takes off what the marker lists (the queue entries it added, each moved entry back to its place, the requests it added); after the lines have left `playlists.conf`, put them back first, so the stores are rebuilt at the next tick, and roll the image back to one from before the queue-only `later.m3u` (homelab#2478's cleanup), which merges the `later` store back into the file.

**Stranded rows** (homelab#2602, `music_fetch.stranded`). An album playlist's row keeps its tracks under the playlist's name, and once the playlist leaves `playlists.conf` nothing reads them: the nightly downloads fallback tracks only for configured playlists, a fallback is searched on Usenet again only for a request, and `feed_requests` drops a dead playlist's tracks only from a requested row. So since the cutover a former `keep` or `later` row with no request that Usenet had missed sat in `fallback` for good, its history ending at `[FALLBACK]`. Now the spotdl fallback never takes such a row (no album playlist's row whose playlists all left `playlists.conf`, and no request: it stays `missing` or `failed`), and each album tick in `on`, right after Later's automatic requests and before the requests are fed, settles every one in `missing`, `failed` or `fallback`, each decision an event with source `stranded`, so `find_events` (kinds `album_dropped`, `album_requested`, `status_changed`; `source=stranded`) lists them:

- **on Later** (an entry names it, by release group or ref): Later owns it, and its automatic requests take it once it has a release group. A `fallback` row goes back to `missing` (`wanted` when it was never searched), its dead fallback tracks dropped, so album mode searches it on Usenet weekly meanwhile (`[STRANDED] … Later requests it once it has a release group`, a `status_changed` event);
- **with a release group** and no request: requested, `requested_by` `auto:stranded` (an `album_requested` event, at most 5 a tick), and fed the same tick, so the request's MusicBrainz tracklist and fallback take over; a release group MusicBrainz gives no tracklist for is dropped as below;
- **never looked up** (`unresolved: pending`: an album with no items, which canon never looks up): its Spotify album is looked up in MusicBrainz with canon's exact rungs (the Spotify URL's link, the ISRCs, the barcode; `music_scan.mb_release`, never a fuzzy match) into the `mb-releases` cache, at most 5 a tick, then the resolve pass keys the row (requested at the next tick) or marks it `no-match`. A Later row with no release group is looked up every tick the same way, which reads a miss again after 7 days;
- **otherwise** (looked up and no release group, a `conflict`, or no Spotify album): the record is dropped as one that leaves its last playlist is, its `album_dropped` event saying why (`[STRANDED] … no playlist in playlists.conf lists it (last: keep) and it has no request; MusicBrainz knows no release group for it …; record dropped`); `album_history` still finds it by its key or Spotify ID, and `request_album` brings it back by hand.

One `[STRANDED]` count line a tick when there is any (`dry-run` only counts). Rolling back to an image from before this leaves the dropped rows gone and the requests in place; a Later row put back to `missing` falls back to spotdl again, stranded as before.

**Hand edits** (homelab#2503). `music-state` makes the edits the runbooks need, each a dry run unless `--apply`: `backoff` lists the spotdl backoff and `clear-backoff` empties it, so the next nightly retries every backed-off track (after new YouTube cookies; `just clear-failures-k8s`); `stores` lists the playlist stores with their Spotify and local entry counts, and `drop-store -- <playlist>` deletes one, so it is rebuilt from Spotify (a spotdl or `nosync` store at the next nightly, an album playlist's when its snapshot changes), saying how many local entries that loses; `clear-snapshot -- <playlist>` forgets an album playlist's Spotify snapshot, so the next album tick re-reads the playlist and writes its store. Each write waits for the locks of the flows that write the same rows, so a run in progress can't write its copy back over it: `pipeline` for the backoff, `albums` then `pipeline` for a store, `albums` (and the album store's save lock) for a snapshot. It records a `state_edited` event (migration 10, `data.what`: `backoff`, `store` or `snapshot`) in the same transaction.

**Postgres down.** The pipeline never runs without its state. Each run skips instead: the album tick logs `[DB-DOWN] Album tick skipped` and pushes `music_albums_tick_success 0`, the scan logs `[DB-DOWN] Scan skipped` (the inbox waits), and the nightly's preflight fails with `state_unavailable`. An album import triggered during the outage fails, and the tick's lost-trigger recovery imports it from SABnzbd history once the database is back.

## Setup

### 1. Clone and prepare

```bash
git clone https://github.com/sometimeskind/music-pipeline
cd music-pipeline
```

### 2. Export YouTube Premium cookies

spotdl requires YouTube Premium cookies for M4A 256 kbps quality.

**Each time cookies expire**, sign in to [music.youtube.com](https://music.youtube.com) in Firefox, then run:

```bash
just cookies
```

This extracts cookies directly from Firefox and saves them to `cookies.txt` (already in `.gitignore`).

Cookies expire every few weeks. Re-export when downloads start failing: the ingest run logs a `YouTube cookies ... look expired` warning, sets the `music_ingest_cookies_expired` gauge to 1, and records the per-track reason (e.g. `HTTP Error 403: Forbidden`) in the backoff (`music-state backoff`). After a re-export, `just clear-failures-k8s` empties the backoff so the next nightly retries every failed track.

Each ingest run also reads the expiry stated in `cookies.txt`: it logs `YouTube auth cookies expire <date>` and pushes the soonest expiry among the Google login cookies (`SID`, `HSID`, `SSID`, `APISID`, `SAPISID`, `__Secure-{1,3}PSID`, `__Secure-{1,3}PAPISID`, `LOGIN_INFO`) as `music_ingest_cookies_expiry_timestamp_seconds`. The homelab alert `MusicCookiesExpiringSoon` fires 7 days before that date. A file with no login cookies (exported signed out) logs a warning and pushes no expiry. The stated expiry is about a year out, and Google usually invalidates a session server-side before then, so `music_ingest_cookies_expired` stays the main signal.

### 3. Set up Spotify credentials

Store your Spotify Developer app credentials in 1Password:

- **Item:** `Personal/Spotify API`
- **Fields:** `username` (client ID), `credential` (client secret)

Create an `.env.tpl` for `op run`:

```bash
SPOTIFY_CLIENT_ID=op://Personal/Spotify API/username
SPOTIFY_CLIENT_SECRET=op://Personal/Spotify API/credential
```

### 4. Register playlists

Edit `config/playlists.conf` and add one line per playlist:

```
# name             spotify-url                                               [flags]
liked-songs        https://open.spotify.com/playlist/37i9dQZF1DXcBWIGoYBM5M
archived-mix       https://open.spotify.com/playlist/37i9dQZF1DXd9rLJfaAKCk  nosync
```

The optional `nosync` flag freezes a playlist: `music-ingest` creates a `.nosync` sentinel on the PVC and never syncs it from Spotify again. Its store is read from Spotify once and then kept, but its want list (the frozen entries no library item holds) is still downloaded every night, in store order and from the shared budget, until the playlist is complete. Each such run logs `[FROZEN-WANT] N track(s)` (homelab#2392). Frozen means the same list, not the same files: a frozen entry may resolve to another copy of the same recording, for example one an album import superseded. A frozen entry Spotify later replaced (a split or relinked track) stays an empty slot until it is fixed by hand. Remove the flag and run `music-ingest` again to unfreeze.

The optional `twoway` and `oneway` flags are for the two-way Navidrome/Spotify playlist sync (homelab#2361), which is not built yet: until it ships they change nothing. Two-way is opt-in: only a `twoway` playlist will ever have Symfonium/Navidrome edits written to Spotify, so no existing or new playlist gets Spotify writes by accident. `oneway` locks a playlist to one-way for good. `twoway` with `oneway`, `nosync` or `album` is a config error that fails the whole load, like a bad Spotify reference.

The optional `album` flag is for playlists that hold only whole albums. spotdl never syncs them (a `.album` sentinel). Instead, the `music-albums` flow downloads each album whole from Usenet through Prowlarr and SABnzbd. Every `ALBUM_POLL_SECONDS` it checks the playlist's Spotify `snapshot_id` and re-reads the tracks only when it has changed, so a playlist edit is picked up within one poll. Then it tops the SABnzbd queue up to `ALBUM_MAX_IN_FLIGHT` within a rolling-24h indexer budget. Its state (album status, release blocklist, indexer use) is the album store in the `music` database (see [State](#state)). Set `ALBUM_MODE=dry-run` first: it searches and logs `[PICK]` lines but never grabs.

**Album playlists sync at the album level (#268).** Spotify decides *which* albums are on the playlist; the local release decides *what is on* each album. An album is on the playlist while at least one of its tracks is, so adding one song on Spotify brings in the whole album: the album counts as `have` only when the library holds every playlist track and at least Spotify's track count of the album's tracks. The `.m3u` lists every local track of every album on the playlist (the items its entries resolve to, and every item canon filed on that Spotify album or, under the same name, on its #214 twin), album by album in playlist order, each in disc/track order, so a release's tracks without a Spotify ID are listed too. A track canon moved to another album (a single's track filed on its standard album) is listed alone. Removing one of an album's tracks on Spotify does nothing; when the last one goes, the tick logs `[GONE] <artist> — <album>: no track left on <playlist>`, and the album's lines leave the `.m3u` at the next regen. The tick writes the playlist's tracklist to its playlist store, as the nightly does for normal playlists. Normal playlists stay track level.

When SABnzbd finishes an album job, its post-processing script POSTs to `/trigger-album-import` (bearer `ALBUM_IMPORT_TOKEN`, which opens only that route). The `music-album-import` flow then:
1. moves the job into `inbox/usenet/<playlist>/`, so beets tags it `sources=<playlist>` and `via=usenet`. A release that posts each audio file loose and again in a RAR set leaves SABnzbd's unpack a `<name>.<N>.<ext>` beside each `<name>.<ext>`, which beets would import as a second copy of each track: before anything reads the job, each such audio file byte-identical to its original is removed (`[DUPFILE] <artist> — <album>: <file> is a byte-identical copy of <original>; skipped`, homelab#2636), so the release match below and beets see each track once. A copy whose content differs stays: it may be another disc or version. An upload can also hold one album in two formats, say a FLAC set and an MP3 set, which beets would import side by side, each track twice and none linkable (`number, several items`): when every file of each format has a twin at the same disc, track and title (case, accents and punctuation aside), in the same folder but for format words, of a length within 5 s, and with no album, ISRC or recording tag disagreeing, only the best format stays, lossless first, then bitrate, judged on the source files, before the conversion to AAC (`[FORMAT] <artist> — <album>: <job> holds its N track(s) as FLAC (870 kbps) and MP3 (320 kbps); keeping FLAC (870 kbps), the rest → quarantine/replaced/retired/`, a `format_dropped` event, homelab#2671). No ID proves that match, so the files aren't deleted: `keep_quarantined` can rescue one until the purge takes it after `REPLACED_RETENTION_DAYS`. The album is the unit: anything less, such as a clean and an explicit set, a second disc reusing the numbers, a real alternate take or a bonus track on one side, imports every file as before, with an info line (`[FORMAT] <job> holds FLAC and MP3, but …; importing them all`). Each file keeps its own title (homelab#2544): beets matches every file alone to the closest MusicBrainz recording, which can be a sibling (a 5.1 mix, an outtake, a live take) or, with a venue suffix and a similar length, another song. So the file's title goes back on over the match's and its `trackdisambig` goes (`[TITLE] <beets' title> → <file's title>`). A title that differs only in case, punctuation or spacing (`In My Time Of Need`, `In My Time of Need`; `Saved theEarth`) keeps MusicBrainz's spelling: no sibling, and it is the better one. Two titles count as two songs only when their letters are less than 80% alike, so a misspelled word in a long title (`Rock River` for `Rockford River`) keeps the recording. When the two titles, version notes dropped (bracketed notes and ` - ` suffixes), are two songs, the recording is wrong too: its IDs, ISRCs and work credits go back to the file's own, usually none (`… (recording dropped)`), and the duplicate check leaves them out as well. So does a match only one side of which names a version (homelab#2609: live, 5.1, demo, alternate, mono, take, outtake, as `music-audit-titles` reads them): *Reason To Believe (Nebraska Live)* matched to the studio recording, or a bare studio *My Father's House* matched to a recording disambiguated `live, 2025‐04‐22: …` (`… (recording dropped: another version, live)`); the recording's disambiguation counts as its title, and the file's album name and its job's cover a bare title, so a live album's tracks keep their live recordings. A sibling's ID used to stay for the recheck, but the duplicate check (`[BOTH]`), the release pass and the purge trust it first: the live take took the studio recording, and the release pass retired it as a copy the library held. Each drop is a `retitled` event whose `data.dropped_why` (`another song`, `another version`) and `data.versions` say why. A same-song sibling with no version word either side keeps its `mb_trackid`, which the fingerprint recheck (below) owns. A file title that names nothing (empty, digits, `Track NN`) keeps beets'; a leading track number that is the file's own (`05 - Song`) is dropped. spotdl imports keep beets' title;
2. runs the scan under the `pipeline` lock;
3. matches the release as a whole to a MusicBrainz release (beets' album matcher, without importing), imports the files beets couldn't match as they are, and records both on the import's event (homelab#2590): `identified` is the release (`mb_albumid`, `album`, `tracks`, `missing` tracks without a file, `unmatched` files), `null` when none is close enough, and `as_is` the count of files imported as they are, on `import_done`, `import_wrong`, `import_incomplete` and the `failure` after an import (the `[RELEASE]`, `[NOMB]` and `[REST]` lines are DEBUG). It stamps the release's items `album_record=<album key>` and `release=<guid>`, and gives them Spotify track IDs as a best effort: by ISRC, then disc and track number when the title agrees (edition notes dropped, #278), never by title words alone;
4. judges the release (#279): **on album playlists the album is the unit, not its tracks.** The release is the album whatever its tracklist (another edition than Spotify's, missing or extra tracks, a file beets couldn't match): `[DONE] … N file(s) from <release>; K of Spotify's M titles not in this release`. Nothing of it is quarantined and nothing it lacks goes to spotdl. Its items take the album's tags from the record (canon, below), and every other copy of the album (an earlier release, items from before #279, spotdl's top-ups) whose recording the release holds moves to `quarantine/replaced/` (`[RETIRE]`). Two copies are one recording only when a Spotify track ID, an ISRC or a MusicBrainz recording ID agrees, never by title (#287). On a `reimport` import, an old release of the record that holds under half of the new release's titles (edition notes dropped; a new release of under 4 titles isn't judged) is another album, and all its items go there too, whatever their recording: `[RETIRE] … another album: holds 3 of the kept release's 13 titles`, with the reason in the `retire` event (homelab#2662). The denominator is the kept release, so a deluxe replaced by its standard edition stays. Titles decide, as two right releases can share no recording. Legacy and spotdl copies, and extras an earlier import left, aren't judged: a deluxe's bonus tracks hold none of the titles. A playlist entry only such an item held goes empty, and the event's `unheld` names the playlists: the import's ID linking may give it to the new release, else a spotdl playlist's nightly downloads it, and an album playlist's slot stays empty. A retired copy first hands the release item holding its recording the Spotify IDs, ISRCs and `sources` that item lacks, as a merge does (homelab#2601): a playlist entry resolves by Spotify ID or ISRC, so a release item that shares only a MusicBrainz recording ID with the copy (another edition's Spotify album, a remaster's ISRC) would otherwise leave the entry resolving to nothing. The `[RETIRE]` line then ends `; <IDs> → <item id>`, and its `retire` event carries `data.ids_to`, `data.spotify_ids` and `data.isrc`. A copy whose recording the release lacks (a deluxe edition's bonus tracks, when the release is the standard edition) is the library's only copy: it stays on the album as a local-only extra (`[LOCAL]`), stamped `album_record` and `album_extra`, so canon files it under the album at the next scan and `music-album-audit-releases` no longer counts the album as mixed. A later release that holds its recording retires it, and so does the release itself once its recording IDs arrive (#294): retire runs before the release gets its Spotify IDs, so a release beets matched to nothing in MusicBrainz (`[NOMB]`) holds no recording yet and keeps every old copy as an extra. Right after the Spotify IDs, and in every scan before canon, an extra whose recording the album's release now holds moves to `quarantine/replaced/` too (`[RETIRE] … (extra, now held)`). An extra none of whose IDs the release holds, but whose audio one release item has (a legacy copy with no IDs, or a release beets matched to another MusicBrainz recording), would otherwise clash with that item at canon every scan (`[CLASH]`): when the pair is in `music-audit-dupes`'s certain tier (an AcoustID match, lengths within 2 s, the same title once edition suffixes are dropped), the extra is merged into the release item as `--apply` would (`[RETIRE] … (extra, same audio): merged into <id>`, then `[MERGE]`; its file to `quarantine/replaced/`), and the next canon files the release item on the canonical path (#301). An uncertain pair, or one whose audio two release items share, stays for the operator. So does a certain group of extras with no release item in it (homelab#2609: a recording two extras share, often a wrong guess one of them took): each extra's `local` event names the others and the evidence (`one track with extra(s) …, and with none of the release's items; left to music-audit-dupes`), once a day while it stands. Both are surfaced (#306): an extra left on the album whose title, edition suffixes dropped, is a release track's is logged once, `[SAMETITLE] <id> <artist> — <title> [<album>] (<length>): the release's <id> (<length>) has its title, but no ID agrees`, and stamped `album_extra_twin`; `music-album-audit-releases` lists those albums after the mixed ones (`[SAMETITLE] <artist> — <album> (<id>): N local-only extra(s) …`), each pair with its `music-audit-dupes --merge` command (the keeper the release item, #311). The title only reports: nothing is merged, tagged or retired by it (track identity is by ID only). A release item whose canonical path such an extra holds is not left behind as a stray album: canon gives it the album's tags where it is (`[CLASH] <id> <path> → <dest>: … tagged in place`, stamped `canon_clash`), and every scan tries the move again until the path is free. Extras take the album's tags at canon, the kept release's `mb_albumid` included (`mb_album_via` `files`), although their files are not from that release: Navidrome groups by the MusicBrainz album ID, so an extra without it would show as an album of its own. Their recording IDs (`mb_trackid`, ISRC, Spotify IDs) stay their own, and `album_extra` marks them. Local-only extras never take a Spotify ID away from the release's own items. Two album records that resolve to one release group merge (`music_fetch.resolve`), and when both had imported, the survivor holds both releases once the scan restamps the absorbed record's items (homelab#2545). Every scan, after the restamp and before the extras above, keeps such a record's own release (its `best_copy` while it waits for a better copy, else the newest release whose import started by its `imported_at`; a merge keeps the survivor's) and retires the rest as an import would: `[MERGED] <artist> — <album> (<id>): keeps its own release <release> (N); retiring …`, then `[RETIRE]` and `[LOCAL]`. A record mid-import or reset for a reimport is left to its import, and one whose own release nothing tells is logged `[MULTI]` and left alone (`music-album-reset --reimport` starts it over). Either decision is a `merged_releases` event (homelab#2601), recorded before the retires: `data.kept` (null for `[MULTI]`, recorded once a day while it stands), `data.why` and `data.releases` (each release stamp's item count), so `album_history` shows which release a merge kept and why. `music-album-audit-releases --merged` lists those records and what the next scan retires of each, read-only; it stays off the MCP, since the next scan does what it lists and the events record it.

A release fails only for a broken download, for being another album (`[WRONG]`: fewer than half of the album's Spotify titles, edition notes dropped, among its items; an album of fewer than 4 tracks, or wanted tracks, is another album only when no item's title holds, or sits inside, one of its titles, and every item has a title, as untagged files prove nothing (homelab#2683); its items go to `quarantine/replaced/`, and on a reimport the old items stay), or for lacking tracks of its own MusicBrainz release (`[INCOMPLETE]`). A failed release is blocklisted and the next one tried. An incomplete copy stays in the library until a more complete one has imported, and the next grab must be the same edition (the edition words in its title: deluxe, remaster, anniversary…), and not an indexer's repost of the copy kept (its title plus `-1`, `.1` or `-FTP`, or the same title; homelab#2593). A first retry, another upload of that edition, still happens, so a REPACK or a broken upload gets its chance; once a retry lacks the same tracks as the copy kept (the same positions of its MusicBrainz release, `lacking` in the identify result; the same count when either copy doesn't record them), the gap is the edition's, not the upload's: the retry goes and the kept copy is the album (`[DONE] … lacks the same N track(s) of its own release as <kept>; the edition lacks them`, homelab#2593). When no copy of that edition is left, or after 3 releases, the most complete copy is the album (`[DONE] … lacks N track(s) of its own release`). Each of the three is an `import_done` event whose `data.why` says which (`edition lacks the same tracks`, `no other copy of the edition`, `the most complete copy after the last attempt`), with the kept copy's `missing` and `lacking`; each `import_incomplete` event carries the copy's `lacking` and, for a retry, `same_gap`. Searches prefer the Spotify album's edition, and take another edition when Usenet has none (`usenet.rank`). After 3 failed releases with no copy kept the album is `failed`, and the last release's quarantined files are kept for review. Usenet tracks never go through the scan's asis pass. An album import hands beets its own job folder (`inbox/usenet/<playlist>/<job>/`) and nothing else, quarantines only that folder's leftovers, and once the release is claimed, tagged and canonicalised, regenerates the `.m3u` files (skipped when a fetch or scan holds `pipeline`: it regenerates them itself) and asks Navidrome to rescan (homelab#2751). The rest of the inbox, and the scan's library-wide steps (the request checks, the asis pass, restamp, merged and held retirements, canon's queue, `beet update`, the purge, the `music_scan` push), are the next scan's: before, every album import ran the whole scan, so a large batch in the inbox imported inside the `albums` lock and held the tick and the connector's album writes for as long as beets took. The import still waits for `pipeline` while holding `albums`, so a scan already running delays it. A trigger that never arrives is recovered from SABnzbd history by the next tick, an hour after the grab. Each import grabs the next album, so imports can run back to back; the tick waits up to 20 minutes for the `albums` lock (`[WAIT]`) and takes the gap between two of them, rather than skip and leave the recovery, the feeds and the fallbacks waiting (homelab#2626). It pushes its own group, job `music_albums_tick` (`music_albums_tick_success`, `music_albums_tick_timestamp_seconds`): an import pushes job `music_albums` too, so only that group says a tick ran. A failure that isn't the release's (#261) costs no attempt: an exception during the import moves the job back to SABnzbd's completed dir and leaves the album `grabbed`, so that recovery imports it again (`[RETRY]`; the third crash in a row counts against the release like a failed import), and a completed job whose dir is gone is searched again at the next top-up, ahead of the queue, without a blocklist entry (`[LOST]`). A pod replaced mid-import leaves the rest of the job in `inbox/usenet/<playlist>/`: at start the service moves it back to SABnzbd's completed dir before anything scans (`[RESUME]`, #344), so the recovery imports it as a retry, its items counted from the first try's start and judged on the first try's MusicBrainz match, instead of a scan importing it loose. The album record names the job (its path and the import's start, and the first try's MusicBrainz match once it is known) in the database from the move into the inbox on, before beets runs (homelab#2603); saved only when the import ended, as before, a replaced pod left nothing to resume, so a scan imported the rest loose and the recovery logged `[LOST]` and grabbed the album again. MusicBrainz being down is not the release's fault either (#264): beets gives up on a request after its own retries (six, with a short backoff, not configurable), skips the track and exits 0, so the scan watches beets' output for `Max retries exceeded` on `musicbrainz.org`. When the import left inbox files behind, it then leaves them in the inbox instead of quarantining them, and the scan fails with `music_scan_last_failure_reason{reason="musicbrainz_unavailable"}`; the album import retries the job the same way (`[RETRY] n/12`, about six hours of ticks) before the release takes the blame. An import that brought in every inbox file despite the errors (beets runs several searches per singleton, so one 503 rarely costs a match) only logs a warning: the scan succeeds and the release is claimed and judged at once (#286). `music-album-reset <artist or album>` (or the album's Spotify ID; an exact `artist — album` wins over the longer names that contain it, #289) undoes an album's last attempt by hand (back to `wanted`, its last release off the blocklist, one attempt fewer, its spotdl queue cleared); `--reimport` starts it over from one release instead (blocklist and attempts cleared, grabbed although the library has its tracks, the old copies retired on import). A reset only clears a release refused for what it held, another album or an incomplete copy: a broken download, or any other failure, stays on the blocklist, so the album goes without rather than be grabbed from it again (homelab#2661). Dry run unless `--apply`. `music-album-audit-releases` lists the imported albums the track-level rules before #279 mixed from several releases or topped up from spotdl (`[MIXED]`), each with its `--reimport` command, then the count of what it read and, by status, of what it didn't (albums not imported, album requests). An album imported whole since #279 is never mixed, and local-only extras and a spotdl copy another playlist also lists don't count (#295): a reimport retires neither; `--replaced '<artist or album>'` lists that album's copies in `quarantine/replaced/` (by their album and artist tags): `[REPLACED]` when a library item holds the file's recording (its Spotify ID, ISRC or `mb_trackid` tags; an `mb_trackid` only from an item within 2s of the file's length, homelab#2540) or the file is a merge's loser whose keeper is still in the library and whose title and artist tags are the keeper's (#303, homelab#2539), `[ONLYCOPY]` when none does or the file has no identity tags. A file a keeper's `merged_files` names but whose title or artist isn't the keeper's (a wrong merge) is logged `[MISMERGED] <file>: <artist> — <title>, but merged onto <keeper id> (<artist> — <title>)` and judged by its identity tags alone. `--apply` deletes the superseded ones only; the only copies stay unless `--only-copies` is given too (#287). `--replaced` without a query lists every only copy in `quarantine/replaced/` (#298), read-only: under each album record that claims it (`[ALBUM] <artist> — <album> (<id>): N only copies`, with that album's `--replaced` command; a file two records claim is under both), then the files no record claims (`[UNCLAIMED]`: a `music-audit-dupes` merge's loser, `music-audit-lengths --replace`'s old audio), each with the item ID its name starts with, its tags and its identity tags. Its totals are the scan's `music_scan_replaced_files{kind}`; it refuses `--apply`, so delete album by album, and unclaimed files by hand. **The album tick does both by itself (#288).** In `on`, before its top-up, it resets mixed albums for a reimport, as `--reimport` does but keeping the blocklist (#305): a release that failed for the album before (another album, an incomplete copy, a broken download, or the track-level rules' `[FAIL]`) is not grabbed again, and a reimport that finds no other release keeps the album it has (`[STAYS]`; it stays mixed, for the operator), rather than going missing and to spotdl. The operator's `--reimport` also clears the releases refused for what they held, to start over when one is wanted after all. The top-up grabs the reset albums in the same tick: `ALBUM_AUTO_REIMPORTS_PER_DAY` in a rolling 24 hours (default 3, `0` turns it off), and only while the grab budget has room for the resets still waiting for their grab. Each reset logs `[AUTORESET] <artist> — <album> (<id>): <why it is mixed>; reimporting`. An album is reset automatically only once (`auto_reimported_at` on the album record); if it is still mixed after its reimport, `music-album-audit-releases` keeps listing it for the operator. Since an album imported whole is never mixed, a clean import, by hand or automatic, is not reset again. An album the operator holds is never reset: `music-overrides hold` (below). Every scan then deletes the files in `quarantine/replaced/` whose recording the library holds once they have sat there `REPLACED_RETENTION_DAYS` (default 14, from the move, the file's ctime; `0` turns it off), logging `[PURGE]`; an only copy is never deleted automatically. A superseded file a person wants kept anyway (the only file of a take whose recording an item holds by a wrong ID) is moved out of the purge's reach with `music-album-audit-releases --keep <file> [--apply]` (the MCP's `keep_quarantined`, homelab#2623): `<file>` is its path relative to `quarantine/replaced/` or the item ID its name starts with (refused when that names no file or several), and the apply moves it to `quarantine/keep/` with a `kept` event. Nothing purges, imports or audits `keep/`; `list_quarantine` with `kind=keep` lists it. Local-only extras a person chose to drop, another recording than the release's, leave with `music-album-audit-releases --retire <item id>... --reason <why> [--apply]` (the MCP's `retire_item`, homelab#2648): their files go to `quarantine/replaced/retired/`, each with a `retire` event, the `.m3u` files are regenerated, and the purge deletes them after `REPLACED_RETENTION_DAYS` as superseded, never as only copies. It refuses the whole call for an item that isn't a settled album's extra, or that is the last item a playlist entry resolves to. The `music_albums` push carries `music_albums_mixed` (imported albums still mixed, counted each tick) and `music_albums_auto_reimports_24h`; the `music_scan` push carries `music_scan_replaced_files{kind="superseded"|"only_copy"}` (what is left after the purge) and `music_scan_replaced_purged_total` (deleted by that scan). An original edition and its remaster on the playlists are two album records that can match the same release (#243): a release another record has in flight is not grabbed again (`[WAIT]`, searched again next tick), and one another record imported or keeps is skipped. Prowlarr searches two indexers, NinjaCentral and NZBNest, so one release can come back under two GUIDs (homelab#2757): the blocklist, the releases other records hold and the in-flight check match a release by its GUID or by its title without a repost suffix. A blocklisted release refused for what it held (another album, an incomplete copy: a *wrong release*) is refused from every indexer. Any other failure, a broken download above all (a *dead download*), blocks only its own GUID, as the other indexer's copy may be another post, and complete: it is tried once, and a second dead copy of the title blocks the rest. An entry whose reason the event store doesn't hold blocks only its GUID. The reset's dry run says which kind each entry is and what it blocks. The copies of one title rank together, by indexer order: the lower Prowlarr indexer ID first, which is NinjaCentral, as each indexer counts only its own grabs.

A job SABnzbd failed goes from its history with its files once the outcome is saved: SABnzbd otherwise keeps the partial download in `incomplete/` for good (homelab#2631).

Searches use the names as release names spell them: diacritics folded, `$` as `s`, apostrophes deleted (`WHACK'S MUSEUM` searches and matches as `whacks museum`). A search with no results is retried once with the artist alone, which counts as a second indexer hit. A title made of glyphs is searched by the artist and matched on size alone (`[PICK] … (artist-only)`). An album whose artist and title are both glyphs is not searched; it logs `[NOWORDS] <album id>: … add a search override`. A search override gives an album its search words, which are both the query and what a release title must contain (`music-overrides search`, below). A missing album is searched again as soon as its query changes (a new override, or a normalisation fix). Spotify's bonus-track count (`Saint Cloud +3`) is dropped from the query and the match, like its bracketed edition notes (homelab#2568). A self-titled album matches a release that names it again right after the artist (`The Meters-The Meters-…`), says self-titled, or carries no other words: `The Meters-The Essentials The Meters` is a compilation (homelab#2568). An album whose name shares a word with its artist, when that word isn't in the title past the artist's name, gets the same treatment: the title must carry no other words (`collection` aside), so `Toto-IV-…` is *Toto IV* but `Curtis Mayfield-Live In Europe-…` is not *Curtis Live!* (`artist words`, homelab#2656). A release title may carry two words beyond the artist, the album and format or edition tags (a year or a number never counts), but not one that makes it another release holding the album's name: `tour`, `live`, `concert(s)`, `unplugged`, `bootleg(s)`, `box`, `boxset`, `acoustic`, `remixes` or `remixed`. `Bruce Springsteen-The Born in the U.S.A. Tour 84-85-…` is a live box set, not *Born In The U.S.A.* (homelab#2604). Such a word still matches when it is the album's own (`Hysteria (Live)`, `MTV Unplugged In New York`) or the artist's (the band Live), and when `edition` follows it (`Special Tour Edition`, a reissue with bonus tracks); deluxe, expanded, remastered and anniversary editions are tags, so they match as before. A live album whose Spotify name doesn't say live, but whose releases do, misses on this rule: a search override with the word fixes it. `[MISS]` lines list the queries sent, so a miss can be checked in the indexer's own search, then why the results were rejected: how many failed each match rule (`album words`, `artist`, `reject word`, `leftover words`, `self-titled`, `other release`, `single`, `size`, or `blocklisted` for one that fails none) and the three closest titles with the rule each failed, e.g. `rejected: 80 album words, 12 artist, 4 size; closest: "Artist-Album-CD-FLAC-1999-GRP" (size: 50 MB, not 70-4000 MB); …` (homelab#2568). A copy kept in the library is replaced only by its own edition, so its `[MISS]` may instead say `N match but not the edition of the copy kept (deluxe)`. An indexer in Prowlarr's failure backoff gets instant empty answers rather than errors, so the tick checks `/api/v1/indexerstatus` before its first search and after every empty result (#263): an indexer in backoff stops the tick with one `[ERR] … indexer in Prowlarr backoff` line, like a failed search, and the album keeps its status. As a guard against an indexer failing silently, 3 albums in a row with no results at all also stop the tick, and the third keeps its status.

A track spotdl's search can't find (`[MISS] … no source found`, e.g. a title made of glyphs) misses again on every retry, so it can be pinned to a source by hand (#247, `music-overrides pin`, below). A pin is a YouTube or YouTube Music video (an ID, or a `youtube.com`, `music.youtube.com` or `youtu.be` URL, reduced to its canonical watch URL, homelab#2411); another site or a playlist is refused, since the URL reaches yt-dlp. The nightly sync downloads a pinned track from that URL instead of searching (`[PIN] <track> → downloading from <url>`), ignores its backoff and spends the budget on it before the playlist's other tracks; the import treats it like any other download. A pin whose track the library already holds logs `[PIN] … already in the library; its pin is unused` and is skipped, so a stale pin can stay until it is tidied.

**Search overrides, holds and pins live in the music database** (homelab#2484, `music_fetch.overrides`), and the tick and the nightly read them on every run, so a change needs no restart. `music-overrides` lists and changes them, every write a dry run unless `--apply`, free text after `--`: `search [--reason=…] -- <album> <words…>`, `clear-search -- <album>`, `hold --reason=… -- <album>`, `release -- <album>`, `pin [--label=…] [--reason=…] -- <track> <https url>`, `unpin -- <track>`, and `list [--kind search|hold|pin]`. An album is anything that names its row: its key, any of its Spotify album IDs or URLs, its release group, or `artist — album`; a track is a Spotify track ID or URL. An override or hold is kept on the album's database row, not its release group, so it holds for an album with none yet, and it follows the row through a merge, or back to the album when an album that left its playlists returns (by its Spotify IDs, name or release group); one that clashes with the row's own stays detached, and `list` shows it. Each write records an `override_set` or `override_cleared` event with its caller in the same transaction; that, and each entry's `set_by`, `set_at` and reason, is the audit trail. The Music MCP's tools run the same command.

They were the homelab ConfigMap's `album-overrides.conf` and `track-pins.conf`. `music-overrides import` (dry run unless `--apply`) copies their entries in once, each with the comment block above it as its reason; an entry no album row has yet is imported detached and attaches when one does; entries held already are skipped. Until it has run (the `overrides-imported` kv marker) the pipeline reads the files, and after it ignores them.

**spotdl fallback (#205).** In `on`, what Usenet can't supply goes to spotdl: a `missing` album (from its first miss) or a `failed` one. An imported release never falls back, and sends nothing to spotdl (#268, #279), and neither does an album playlist's row whose playlists all left `playlists.conf` (homelab#2602, Stranded rows above). spotdl fetches the Spotify album's whole tracklist, not just the playlist's tracks: the tick reads it once per album (two Spotify calls, `album_songs` on the album record, up to 10 albums a tick), and until then the playlist's tracks stand in. The album becomes `fallback` (`[FALLBACK] … N track(s) left to spotdl (<why>)`), its absent tracks' Spotify IDs are kept in `fallback_tracks` under its first playlist, and album mode no longer searches it. A record from before #268 whose fallback came from an imported release (`fallback_from: partial` or `gap`) is settled by the next tick: `imported`, `settled_from` keeps why, the tracks spotdl already fetched stay and the rest leave its queue (`[SETTLED]`). The nightly sync downloads those tracks into the album playlist's inbox at the playlist's place in `playlists.conf` order, from the same `SYNC_TRACK_LIMIT` budget, with the usual `[HAVE]` check and backoff, and never rewrites the album playlist's store. Once the library holds every track of the album's tracklist the tick marks the album `filled` (`[FILLED]`). `music_albums{status="fallback"|"filled"}` and `music_albums_fallback_tracks` (tracks waiting) are on the `music_albums` push. `music-album-requeue [<album id>…] [--since <ISO time>]` puts albums a miss demoted (`fallback_from: missing`) back to `wanted`, by key or by when they fell back, and takes their tracks spotdl hasn't downloaded yet off its queue; dry run unless `--apply`. It is the recovery for misses that were really an indexer outage.

**Album record events (homelab#2590).** Each change to an album record is an event, so `album_history` answers "why did (or didn't) this album move": a record a feed creates logs `[QUEUED] <key> <artist> — <album>: new <origin> record (<why>)` (`album_queued`), and one the album-playlist or library feed drops logs `[DROPPED] … record dropped` (`album_dropped`, as the wants feed's `[UNWANTED]`). A search that matches nothing is a `search_miss` event with the `[MISS]` line, its queries, result count and `why` (one a day for the same line). A grab the indexer refuses is a `failure` with `data.what: grab` and `gave_up: false`. A status change no other event names is `status_changed` (`data.from`, `data.to`, `data.why`): `[NOWORDS]`, `[STAYS]`, `[SETTLED]`, and an album the library already holds (`[HELD] … not searched`, status `have`). `music-album-reset --apply` (the MCP's `reset_album`) records `reset` (`[RESET] <artist> — <album> (<key>): <status> → wanted`, the changed fields in `data.before` and `data.after`, `data.reimport`) and `music-album-requeue --apply` (`requeue_albums`) records `requeued` (`[REQUEUE] …`); a dry run records nothing. The resolve pass records each merge as `album_merged` (`[MERGE]`, the absorbed records in `data.absorbed`) and each record it keys by a release group as `spotify_id_resolved` (`[REKEY]`, `data.via`), on the tick and on `music-album-resolve --apply`. Evidence the import outranked is `data.conflict` on that rekey; on an `album_merged`, `data.conflict` is an absorbed record's outranked evidence or differing search overrides. A record left unkeyed because its evidence names two release groups is a `conflict` event (`[CONFLICT]`, once a day while it stands). `music-audit-lengths --replace --apply` (`replace_item`) records `replaced` on the item: both sources, the old path and where the old file went (`data.quarantined`). An import records its items' changes too: a spotdl download imported into the library is `imported` on the item (`[IMPORTED] <playlist>: <artist> — <title>`, its IDs in `data`; a request's verified fallback says so), and a Usenet track whose title or trackdisambig the import put back from its file is `retitled` (the `[TITLE]` line, `data.matched` and `data.recording_dropped`). A Usenet import's items get no `imported`: the album's `[DONE]` is that event. At import neither usually has an album key to carry (canon and the release check stamp it later), so read them with `find_events` by kind or item ID. The scan's later changes to items are events too (migration 20): each canon run records one `retagged` event per album it changed items on (`[RETAG] <album artist> — <album>: N item(s) retagged (<fields>), M moved`, each item's changed fields, old and new, in `data.items`; per album, since canon retags about 3,000 items a day on about 300 albums; a move between Spotify albums is still a `moved` event on its item too). A stamp moved to its album's row is `restamped` (one per album, `data.from`, `data.items`). A superseded file deleted from `quarantine/replaced/` is `purged` on the item it was (the scan's `[PURGE]`, and `music-album-audit-releases --replaced --apply` on its album, `data.only_copy`). An album request's fallback track stamped with its record is `claimed` (`[CLAIM]`), and one left unstamped is `claimed` with `data.claimed: false` (`[UNCLAIMED]`, once a day while it stands). The Spotify track IDs linked to a Usenet release's items are one `id_linked` event per import (`[IDS] <playlist>: N Spotify track ID(s) linked …`, `data.linked` with each ID's rung, `data.skipped` with the `[AMBIG]` and `[NUMBER]` tracks). The nightly and the queues record theirs (migration 21): a spotdl track with no source backs off as a `failure` (`[MISS]`, `data.kind: miss`, as a `[FAIL]` already did); a playlist that left `playlists.conf` has its store dropped as `state_edited` (`data.what: store`), and a local entry its store now resolves as `state_edited` (`[STORE-TAIL]`, `data.what: store_tail`; the line is DEBUG when nothing resolved, as it is for nearly every playlist every scan); a Navidrome playlist the sweep deletes is `playlist_deleted`; a Later entry resolved to its album's release group is `later_resolved` and one now held whole `later_available`; an override or hold that moves to its album's new row is `override_set` with `data.reattached`; and the request feed records a new record (`album_queued`), a wants or library record it takes over and a retired playlist's tracklist giving way to the request's (`album_requested`, `data.what` `took_over` or `stands_in`). A spotdl download itself is no event: it either imports (`imported`) or is rejected (`reject`).

**Paths that differ only in case (homelab#2742).** Navidrome links a `.m3u` line to a file case-insensitively (SQLite `NOCASE` over NFC and NFD forms), so of two files whose paths differ only in ASCII case, or only in Unicode normalisation, a playlist plays whichever its query returns. The library's filesystem is case sensitive, so beets' unique-path check (the `.1` it gives a taken destination) never saw such a twin: a spotdl copy `Hot Chip/In Our Heads/04 - Look At Where We Are.m4a` and a later Usenet import's `04 - Look at Where We Are.m4a` (MusicBrainz's capitalisation) sat side by side. Every move through beets (the import, playlist and Usenet album alike, the as-is pass, `beet update`, `beet move`) now treats a destination that folds (`music_scan.pathfold.fold`, as Navidrome compares) to another item's path as taken, and gives the item the next `.N` name, logged `[CASECLASH] <id>: <dest> differs from another item's path only in case; placed at <path>`; the item keeps it while the twin stands and takes its own path once it is free, as for an exact clash (homelab#2723). Canon does the same (below). Items already in the library are not moved by it: `music-audit-case-twins` lists them.

**Import-time duplicates (homelab#2590).** When the duplicate check imports a track beside a library item, each item it goes beside is an event on the imported item, written once beets has stored it (so an import that fails records none): `import_alongside` for the same recording (`[BOTH]`, `[ALBUM] … which supersedes it`) and `kept_apart` for a track with the same artist and title that no ID links (`[SPLIT]`, `[APART]`). `data.why` says which case and `data.duplicate` names the library item (`item_id`, `via`, `isrc` and its path). They are per item, about 300 a day; the log lines stay, since an import, not every scan, writes them.

**Usenet first for spotdl playlists (#324).** Every spotdl playlist (no `album` or `nosync` flag) stays a spotdl playlist (nightly sync, track-level `.m3u`), but each album holding `ALBUM_WANT_MIN` (default 2; `0` turns this off) or more of its wanted tracks is grabbed whole from Usenet by album mode, and spotdl's nightly budget goes to the rest. At every album tick each playlist's want list (as the nightly computes it, backoff not applied) is grouped by album, and the threshold counts across playlists: one wanted track on each of two playlists is two (a track both list counts once). Each album at or over it becomes an album record with `origin: "wants"` holding each playlist's wanted tracks only, searched after the album playlists' records, most wanted first, then by its first wanted track (playlists in `playlists.conf` order, then position). Skipped, so their tracks stay on spotdl: albums with no Spotify album ID (local files), and an album an `album` playlist already wants whole (an album playlist that adds a wants record's album takes the record over). A wants record whose album falls under the threshold (its tracks removed on Spotify, or downloaded another way) is dropped while it is `wanted`, `dry-run`, `missing` or `have`, unless it was reset to import again (`reimport`, homelab#2544): its album is in the library, so no want list names it. A drop logs `[UNWANTED] <key> <artist> — <album>: no want list holds it any more; record dropped` and records an `album_dropped` event (`data.status`, `data.playlists`), which `album_history` still finds by the album's key, Spotify ID or release group once the record is gone. **The hold reaches only the next few grabs:** in `on`, a wants record's tracks are held off spotdl's want list while it is `grabbed`, or `wanted` and among the first records, in search order, that the next `ALBUM_MAX_IN_FLIGHT` × `ALBUM_WANT_HOLD_AHEAD` grabs (default 3 × 4; never more than `ALBUM_GRABS_PER_DAY`) reach after the album playlists' `wanted` records. SABnzbd's queue sets the pace, not the grab budget, so the rest of the queue stays on spotdl until its turn nears, so a long queue never starves the nightly; an album spotdl completes meanwhile drops out of the queue. The import is album mode's (the release is imported whole, other copies superseded), and the wanted tracks reach the playlist's `.m3u` at the next scan. Unlike an album playlist's record, a wanted track the release lacks goes back to spotdl, and a `missing` or `failed` record queues no whole-album fallback: its wanted tracks just return to the want list (a `missing` one is searched again after a week). The grab and indexer budgets are shared, album playlists first. Each tick logs `[WANTS] <playlist>: N album(s) queued (M wanted track(s)), K held off spotdl` (plus the skips), the `[GRAB]`/`[DONE]` lines name the playlist (`(wants: <playlist>)`), and the `music_albums` push carries `music_albums_status{status, origin}` (`origin` `album` or `wants`) beside `music_albums{status}`. `music-audit-want-albums` leaves the held tracks out, so it shows what is left for spotdl.

**Library-wide (homelab#2403).** `ALBUM_LIBRARY` (`off`, the default; `dry-run`; `on`) extends the rule to the whole library: an album is grabbed whole when `ALBUM_WANT_MIN` or more of its tracks are referenced, counting the library's items by `spotify_album_id` (one per recording, playlisted or not) and every store's wanted tracks (album and `nosync` playlists included), even when none of them is missing. Skipped: albums the library holds whole (Spotify's track count, or placed by a release import), local keys, albums an album playlist's or a wants record has (the wants feed runs first and takes a waiting library record over), and albums no store lists a track of (the import files an album under a playlist; `[LIBRARY] … no playlist track skipped`). Each becomes a record with `origin: "library"` whose `playlists` hold every store track on the album, held or wanted, so `have` and the import treat it as an album playlist's: it is `have` once the library holds it whole, and after the import supersede replaces the loose copies. It is searched after the album playlists' and the wants records, most referenced first, shares their budgets and their hold, and never falls back (a wanted track the release lacks stays with spotdl). A waiting library record whose album no longer qualifies is dropped. `dry-run` queues nothing and logs `[LIBRARY] dry-run: N album(s) would be queued (M new)` and the first ten; `on` logs `[LIBRARY] N album(s) queued (M new), K held off spotdl`; `off` (or `ALBUM_WANT_MIN=0`) drops the waiting library records. `music_albums_status` carries `origin="library"`. `music-audit-want-albums --library` is its baseline.

This file is the single source of truth for playlists. `music-ingest` reconciles disk state to match it on every run — provisioning new entries, reconciling the `.nosync` and `.album` sentinels, and deleting the playlist store and `.m3u` of a playlist removed from it. Navidrome imports each `.m3u` as a synced playlist and keeps it when the file goes, so the reconcile then sweeps Navidrome (homelab#2541, `music_scan.navidrome.sweep_playlists`): through Navidrome's native API (the Subsonic API's playlists carry no file path), it deletes each playlist whose file path is in Navidrome's view of `playlists/` (`NAVIDROME_PLAYLISTS_DIR`) and gone from the pipeline's, with sync on, logging `[NAVIDROME] deleted playlist <name>: imported from <path>, which is gone`. The match is by file path, never by name: a playlist made in Navidrome has no path and is never touched, even with a removed playlist's name. A playlist still in `playlists.conf` is left (its `.m3u` is due back), and so is one whose sync the operator turned off in Navidrome. A Navidrome failure is logged and doesn't fail the reconcile; every nightly sweeps, so the next one retries. Navidrome's scanner imports the playlists as its first admin, private, so `NAVIDROME_USER` must be a Navidrome admin to see and delete them (a warning says so when it isn't).

**Playlist shadow check** (homelab#2361). `music-playlist-shadow [-v] [playlist …]` compares each playlist's Navidrome playlist with its store's Navidrome view, read-only, to check the Navidrome → beets mapping the two-way sync will rely on before it writes anything. For each store (not `later`) it reads the Navidrome playlist imported from its `.m3u` (matched by file path under `NAVIDROME_PLAYLISTS_DIR`, never by name) through the native API, maps each track's path to the pipeline's (`NAVIDROME_MUSIC_DIR` swapped for `/root/Music`) and that to a beets item, and logs `[SHADOW] <playlist>: view N, navidrome M, would add A, would delete D, unmapped U, missing X, order same|differs`. *would add* is a track on an item the view lacks, *would delete* a view entry no track holds (what a two-way engine would misread as a local delete), *unmapped* a track on no beets item, *missing* one Navidrome flags missing. Every Navidrome playlist follows its `.m3u` today, so all should be 0 with the order the same; right after a scan, before Navidrome has rescanned, a difference can be timing, so run it again. `-v` lists the entries. It is skipped while Navidrome scans, writes nothing (no store, no Navidrome, no event), and exits 1 only when Navidrome can't be read.

**Two-way playlist sync, dry-run** (homelab#2361, `music_scan.playlist_sync_cycle`). With `PLAYLIST_SYNC=dry-run` the `music-playlist-sync` flow runs a cycle every 5 minutes (the first a minute after the service starts; `off`, the default, leaves the deployment unscheduled). It covers every playlist in `playlists.conf` without `oneway`, `nosync` or `album` (narrowed by `PLAYLIST_SYNC_PLAYLISTS`). For each it reads the store, each entry resolved by its `store_view` slot (so never differently from the `.m3u`), the Navidrome playlist imported from its `.m3u` (as the shadow check finds it; of two from one file, the first with sync on, with a warning) and its snapshot, and hands them to the merge core (`music_scan.playlist_sync.plan`). A track maps to a beets item by its path compared the way Navidrome links a `.m3u` line to a file (NFC, ASCII case folded: SQLite `NOCASE`), since of two files whose paths differ only in case Navidrome may link either (homelab#2742); of several items on one path the track is the view's, else the snapshot's, else `ambiguous` (a pending kind, never a local add). It reports what the first `on` cycle would do and writes nothing to Spotify, Navidrome or the store, and records no event. The first cycle that reads a playlist takes its snapshot; a dry run never advances it, so an edit made in Symfonium stays pending all week rather than being absorbed. A playlist that leaves the coverage through `playlists.conf` (removed, or flagged) loses its snapshot, and one that comes back takes a fresh one. A cycle is skipped while the `pipeline` slot is taken (`busy`; probed, not held, so a scan never finds it held by the sync) or Navidrome scans (`scanning`), and both are checked again at the end, discarding the cycle when either changed. A playlist sits a cycle out when its `.m3u` is newer than the Navidrome playlist's `updatedAt`: the scan has rewritten it and Navidrome hasn't re-imported it yet. It also sits out when it has no imported Navidrome playlist, when sync is off on it in Navidrome, or when it can't be read. Logged: `[SYNC-DRY] <playlist>: view V, navidrome N, local delete …, unmapped U` (INFO when a local delete, local add, promotion or would-trip is pending, with the items listed; DEBUG otherwise), `[SYNC-DRY] <playlist>: snapshot taken …` and one `[SYNC] dry-run cycle ok …` line. Pushed: `music_playlist_sync_outcome{outcome}` (`ok`, `busy`, `scanning`, `error`; 1 for this cycle's) and `music_playlist_sync_last_cycle_timestamp_seconds` every cycle (job `music_playlist_sync`); after an `ok` cycle (job `music_playlist_sync_ok`) `music_playlist_sync_last_ok_timestamp_seconds`, `music_playlist_sync_duration_seconds`, `music_playlist_sync_pending{playlist,kind}` (`Plan.pending()`'s kinds, for compared playlists only, so a skipped one never reads as zero), `music_playlist_sync_would_trip{playlist,rule}` and `music_playlist_sync_skipped{playlist,reason}`. A failed cycle is the `error` outcome, never a failed flow run.

### 5. Run the first ingest

```bash
just fetch
```

This writes a playlist store for every entry in `playlists.conf` and begins downloading. To add or remove playlists later, just edit `playlists.conf` and run `just fetch` again.

### 6. Start the service

```bash
op run --env-file=.env.tpl -- docker compose up
```

This starts the Prefect server and the `music-pipeline` service. The fetch flow runs daily at 03:00 UTC by default — override with the `FETCH_CRON` env var. The scan flow runs automatically whenever new audio files arrive in the inbox.

To avoid rate limiting on large playlists, set `SYNC_TRACK_LIMIT` to cap total new downloads per session across all playlists. The pipeline resumes where it left off on the next run.

## Kubernetes deployment

This section contains everything an agent needs to write the k8s manifests.
The canonical manifests live in the homelab repo.

### Architecture

One long-running `Deployment` for the `music-pipeline` service, plus an optional `Deployment` for the Prefect server (for the UI and flow run history). Scheduling is handled internally by Prefect via the `FETCH_CRON` env var — no k8s CronJobs needed.

The Music MCP adapter ([`mcp/`](mcp/README.md), `ghcr.io/sometimeskind/music-mcp`) is a separate `Deployment` in its own namespace that talks to this service's `/mcp-api/*` only.

Without `PREFECT_API_URL` set, the service runs in direct mode: flows execute in-process and the Prefect server is not required. Use this for a simpler deployment with no UI.

### Typical k8s playlist workflow

Playlist management is fully declarative: edit `config/playlists.conf` and update the `music-pipeline-playlists` ConfigMap. The next fetch flow run reconciles disk state automatically.

**Add a new playlist:**
1. Add the entry to `config/playlists.conf`, commit and push.
2. Update the `music-pipeline-playlists` ConfigMap (or let GitOps do it).
3. The next scheduled fetch run writes its playlist store and begins syncing.

**Freeze a playlist (stop syncing):**
1. Add `nosync` as the third field on the playlist's line in `config/playlists.conf`.
2. Update the `music-pipeline-playlists` ConfigMap.
3. The next fetch run creates the `.nosync` sentinel automatically. A playlist frozen before its first sync is read from Spotify once and then downloads its missing tracks over the following nights.

**Remove a playlist:**
1. Remove the entry from `config/playlists.conf`, commit and push.
2. Update the `music-pipeline-playlists` ConfigMap.
3. The next fetch run deletes its playlist store, `.m3u` and inbox dir. Its tracks stay in the library, and their `sources` still name it (where they came from).

**Trigger a manual fetch now:**
```bash
kubectl exec -n <ns> deploy/music-pipeline -- \
  curl -s -X POST http://localhost:8080/fetch/trigger \
    -H "Authorization: Bearer <token>"
```

**Backfill track identity (once, #176):** items imported before Spotify IDs and ISRCs were stored get them from the playlists' Spotify pages (about one call per 100 tracks). It also lists **wrong versions**: playlist entries an older artist+title duplicate check merged into a different recording (live, remaster, radio edit). A candidate whose ISRC MusicBrainz lists on the item's recording (`mb_trackid`) is the same recording under another ISRC, not a wrong version (`[SAME]`); only those candidates are looked up, at one MusicBrainz call a second. `--apply` writes an item's new ISRCs to its file's tags before storing them, under the pipeline lock (homelab#2726: an ISRC the database alone held went back to the file's at the next scan's `beet update`). Each item it writes is an `ids_written` event, its `changed` field holding each of `spotify_ids`, `words_ids`, `isrc` and `sources` that changed, old and new (homelab#2590).
```bash
kubectl exec -n <ns> deploy/music-pipeline -- music-backfill-ids                            # dry run: report only
kubectl exec -n <ns> deploy/music-pipeline -- music-backfill-ids --apply                    # write IDs and ISRCs
kubectl exec -n <ns> deploy/music-pipeline -- music-backfill-ids --apply --redownload 10    # also fetch 10 right versions
```

**Backfill imported albums' empty entries (homelab#2664):** `music-backfill-ids --albums` runs the number rung above over the albums already imported, for each entry no library item holds by Spotify ID or ISRC. It reads no Spotify pages and uses no title words. It writes `spotify_ids` and `words_ids` in the database only, moves no file, then regenerates the `.m3u` files and rescans Navidrome. An entry nothing holds has no item sharing its ID, so no retire, supersede or merge follows. The dry run prints a `[LINK]` line per link, a `[NOID]` line per entry left empty with the reason, and the totals. It is the Music MCP's write tool `backfill_album_ids`; `unlink_spotify_id` undoes one link.
```bash
kubectl exec -n <ns> deploy/music-pipeline -- music-backfill-ids --albums           # dry run
kubectl exec -n <ns> deploy/music-pipeline -- music-backfill-ids --albums --apply   # write, regenerate the .m3u files, rescan Navidrome
```

**Audit and replace wrong audio (#165):** nothing checks a playlist download's length at import (the length guard was dropped, homelab#2579: it never ran under the Prefect scan, and would have rejected about one in 320 downloads), so a wrong download is found and fixed here. `music-audit-lengths` reads every playlist (`nosync` and `album` ones too) from its Spotify pages (about one call per 100 tracks) and lists `[SUSPECT]` items whose length is off from the Spotify entry's by more than 10% and 5s, with the YouTube video spotdl downloaded them from. Its last line counts what it didn't compare: entries with no library item or no Spotify duration, and library items on no playlist, and says whether silence was checked. `--replace` re-downloads one item, pinned to a YouTube video, and swaps the file **in place**: the item keeps its id, tags, playlists and IDs, and the old file goes to `quarantine/replaced/`. Going through the inbox doesn't work, since the duplicate hook would merge the new file into the old item by Spotify ID and drop it.
```bash
kubectl exec -n <ns> deploy/music-pipeline -- music-audit-lengths                         # report suspects
kubectl exec -n <ns> deploy/music-pipeline -- music-audit-lengths --silence --quarantine  # also mid-track silence; checks over quarantine
kubectl exec -n <ns> deploy/music-pipeline -- music-audit-lengths --replace <id> --youtube <url>          # dry run
kubectl exec -n <ns> deploy/music-pipeline -- music-audit-lengths --replace <id> --youtube <url> --apply  # replace
```
Without `--youtube` spotdl searches again and usually picks the same video; the replace then stops. A download that fails the length or silence check is refused unless `--force`.
`--redownload` downloads into the playlist's inbox (works for `nosync` and `album` playlists too) and takes the playlist off the wrong item; the next scan imports the download as its own recording.

**Duplicates (#210):** `music-audit-dupes` finds duplicates already in the library, in two tiers. **Certain:** a shared Spotify ID or ISRC, a shared MusicBrainz recording ID with lengths within 2s (homelab#2540: beets imports singletons and names each file's recording by a best guess, so a 5.1 mix or a live take can share a stereo or studio track's ID at another length), or an AcoustID match (shared `acoustid_id`, or fingerprints compared between items that share an artist word) with lengths within 2s and the same title once edition suffixes are dropped. **Uncertain:** title+artist only (the album matcher's normalisation), or an AcoustID match or shared recording ID with lengths further apart, or between different titles (likely a wrong download: fix it with `--replace` above, never a merge); listed, never merged by `--apply`, since a demo or live take must stay its own item. Title+artist pairs with disjoint ISRCs are the duplicate hook's `[SPLIT]` decision and are only counted. On album playlists the album is the unit (#279), so a certain group whose items sit on different album records (a greatest-hits and the studio album), or that holds two tracks of one album record (a deluxe listing a recording twice: two release items, or two local-only extras and no release item), is not merged by `--apply` (#311): it is listed `[ALBUM]` with the reason and a `--merge` command per pair, for the operator. An extra and its own record's release item are one album's copies and merge. `--apply` merges each other certain group onto an album record's release item, else one of its extras, so the album keeps its track; then the item whose length is closest to Spotify's (then bitrate, playlists, the older item): it takes the others' `spotify_ids`, `isrc`, `sources` and a missing `mb_trackid` when MusicBrainz titles that recording as the keeper's song (homelab#2600: a dropped item's ID can be a sibling recording's, guessed by a singleton import, and a failed lookup takes none; `[NOTRACKID]` and the `merge` event's `mb_trackid_refused` say why), their files move to `quarantine/replaced/` (never deleted), the `.m3u` files are regenerated, then Navidrome rescans. The keeper records the moved files' names in its `merged_files` flex attribute (`/`-separated, passed on when it is merged in turn), so they count as superseded and the purge deletes them while it is in the library, whatever the loser's own identity tags (none, or an `mb_trackid` the keeper lacks, #303). A name is not an ID, though: a wrong merge leaves its loser's name there (unlinking the wrong Spotify ID doesn't take it out, and a later merge carries it on), so a file counts this way only while its title (edition notes dropped) is the keeper's and their artists share a word when both are known (homelab#2539). Otherwise, and for an untitled or unreadable file, only its identity tags count, and with none held it is an only copy and stays; `music-album-audit-releases --replaced` logs it `[MISMERGED]`. Once the keeper leaves the library they are only copies again. The keeper isn't moved; run `music-canon-albums` afterwards to file it under its album. **`--merge <keep> <drop>...` merges a pair you have confirmed (#276)**, usually from the uncertain tier, which prints the command for each of its pairs (`if one recording: music-audit-dupes --merge 2898 92`, keeper by the same rule; a group of three prints one per pair, so copy only the pairs that are one recording; a pair two rules found prints once). It goes through the same merge as `--apply` (the keeper takes the drops' IDs, playlists and a missing `mb_trackid` checked as above, which the dry run shows, their files go to `quarantine/replaced/`, the `.m3u` files are regenerated and Navidrome rescans), under the pipeline lock. Without `--apply` it prints the keep/drop block and what moves. It refuses unknown IDs, the keeper among the drops, and a manually imported drop (any `via` but spotdl/usenet) unless `--allow-manual`. A drop that is a track of an album record merges too, with a warning (`[ALBUM] <id> is a release item of album record <id> [<album>]: its album loses the track`), unless it is merged into a release item of its own record (an extra, or a twin release item such as a `.1` copy): the album keeps the track through the keeper. **`--unlink <id> <spotify track id>` takes one Spotify ID off one item (homelab#2530).** A playlist entry resolves by Spotify ID before ISRC, so an item that wrongly holds an entry's ID (a wrong merge brought it along: its `merged_files` names the entry's song) takes the slot even when the right item is in the library and holds the entry's ISRC. Without `--apply` it prints the item's `spotify_ids` before and after and, for each playlist entry with the ID, the item it resolves to afterwards (the lowest item holding the ID, else the ISRC) or that the slot goes empty. With `--apply` it stores the item, records a `wrong_version` event, regenerates the `.m3u` files and rescans Navidrome, under the pipeline lock. It refuses an ID the item doesn't hold, and the item's `spotify_url` ID (the file was downloaded for that entry: a wrong download is `--replace`d, not unlinked). Undo it with `beet modify id:<id> spotify_ids=<before>`. Each audit pushes `music_dupes_groups{tier}` (Pushgateway job `music_audit_dupes`; the `[ALBUM]` groups count as uncertain). `chroma` fingerprints only autotagged imports, so asis imports had none; the plugin now fingerprints them at import, and `music-audit-lengths --replace` refingerprints the new audio. For the items already in the library, `--fingerprint --apply` writes one to the file's tags and stores it for each item without (homelab#2723: one the database alone held was gone after the next scan), so run it first; `--fingerprint <id>...` recomputes items replaced before this, which still carry the old audio's fingerprint. An audit ends by counting the items it had no fingerprint or no title words to compare.
```bash
kubectl exec -n <ns> deploy/music-pipeline -- music-audit-dupes --fingerprint           # count items without a fingerprint
kubectl exec -n <ns> deploy/music-pipeline -- music-audit-dupes --fingerprint --apply   # fingerprint and store them
kubectl exec -n <ns> deploy/music-pipeline -- music-audit-dupes --fingerprint 873 615 --apply  # refingerprint these items (the MCP's fingerprint_items)
```

**Guessed recording IDs (homelab#2543):** beets imports every file as a singleton and names its recording (`mb_trackid`) by a guess from title, artist and length, so a sibling recording can win: a 5.1 mix for a stereo track, a live take for a studio one, an alternate version. `music-mb-fingerprint --recheck` checks each item that has an `mb_trackid` against its own audio: it looks the file up on AcoustID (no MusicBrainz calls; pyacoustid keeps to AcoustID's 3 requests a second, so the whole library takes hours) and reports `[RECHECK] <id> — <title>: mb_trackid <guess> is not among its AcoustID recordings (<top> <score>): …` when the guess isn't among the recordings AcoustID links to the fingerprint at 0.85 or more. With exactly one such recording the line ends `→ <recording>`, and `--apply` replaces the guess with it. With several, none is chosen and the item is left alone. AcoustID having nothing at 0.85 is `[NOMATCH]`, left alone too (some releases are unknown to it). A request fallback's item (`fallback_recording`, which AcoustID already named) is skipped. A merge or supersede keeper (`merged_files`) is checked and replaced like any item, and marked `(a merge keeper)`: a merge joins only copies with the same audio or a shared ID, so the ID it carries from a loser is that loser's guess, and its losers' files stay superseded by `merged_files` (while their title and artist are the keeper's, homelab#2539). A `[SUMMARY]` line gives the counts checked, agreeing, flagged (replaceable, with several recordings, merge keepers among them), no match, errors, gone and skipped, and with `--apply` the count replaced. Item IDs after the flags limit the run to those items. `[PROGRESS] <n>/<total>, <x> flagged so far` every 500 items says how far a whole-library run has got. The lookups run without a lock, so the pipeline's ticks go on during the run and may move, retire or purge a file: each item is re-read from the library just before its lookup, and one gone from the library, or whose file went away between the read and the fingerprint, is logged `[GONE]`, counted in the summary and not checked (re-run with its ID). Start a whole-library run just after an album tick, so the fewest files move under it. `--apply` then takes the pipeline lock and, item by item, skips one whose `mb_trackid` changed meanwhile, and stores the new ID with a `recording_replaced` event (migration 11; `data.old`, `data.new`, `data.score`) in the same transaction. It refuses to run without `MUSIC_DATABASE_URL`. Then it writes the file's tags. The fields beets copied from the guessed recording go with it (homelab#2544): each replaced item's `trackdisambig` becomes the new recording's disambiguation on MusicBrainz (often empty) and its `title` the new recording's title, in the same store, logged `[REFRESH] <id>: title '<before>' → '<after>'; trackdisambig '<before>' → '<after>'` and kept in the event as `data.refreshed`. A Usenet album track (`via=usenet`) keeps its title, which is its release file's own (above), while it is the same song as the recording's (version notes dropped) and names no version (5.1, live, demo, alternate, mono, take, outtake) that the recording's title and disambiguation don't: a track imported before that fix still carries the guess's *(5.1 mix)* or another song's name, and those go. The lookups go through the pipeline's MusicBrainz client (one request a second, a 503 retried once), so an apply takes about a second an item. That lookup is also the only check that the recording AcoustID named is the item's song (homelab#2583), so an item whose lookup fails (`[NOREFRESH]`) is not replaced: `[SKIP] <id> — <title>: MusicBrainz couldn't be asked whether its new recording is the same song; run it again; mb_trackid <guess> left alone`. A new recording whose title names another song than the item's (less than 80% alike, version notes dropped) logs `[SUSPECT]`: either the recheck matched the wrong recording (an AcoustID collision) or the file is a wrong download, and both want a person, not a title that hides it (homelab#2544). An apply doesn't replace such an item (`[SKIP] … its new recording names another song; check it by hand`, homelab#2583: the 2026-10-31 apply gave six items another song's recording); `--refresh-replaced` leaves one replaced before that alone. A recorded run's apply records both skips as the finding's outcome, and its `[SUMMARY]` counts them as not replaced; running the apply again retries them. `--refresh-replaced` lists them in its summary. ISRCs, the work and its credits, `mb_releasetrackid` and the artist are left as they were: ISRCs are an identity key like `mb_trackid`, which playlist entries resolve by, and an item's ISRCs mix spotdl's, the match's and a merge's with nothing to tell them apart; beets' singleton lookup asks MusicBrainz for no work relations, so the work is the file's own. `music-mb-fingerprint --refresh-replaced` does the same refresh for items already replaced (each item's latest `recording_replaced` event; `--since <ISO time>` for the later ones only, UTC unless it says otherwise): a dry run lists each change (`[WOULD-REFRESH] <id> — <title>: title '…' → '…'`), and `--apply` makes them under the pipeline lock and writes the tags, re-reading each item first, each change recorded as a `recording_refreshed` event (migration 13; `data.recording`, `data.refreshed` before → after), so `album_history` shows it beside the album's other events. It never changes `mb_trackid`: an item whose `mb_trackid` is no longer its event's recording is skipped, and so is one whose lookup fails (the `[SUMMARY]` lists them; run it again). Running it again changes nothing new. Navidrome identifies a track by its `mb_trackid`, so a replaced item may show as a new track there, without its play count and stars (accepted by the operator, 2026-10-31). Undo one with `beet modify id:<id> mb_trackid=<old>` (the event's `data.old`). Run with no mode flag, `music-mb-fingerprint` writes nothing and says which modes there are: its old fill mode (first AcoustID result, no event) is retired (homelab#2640); a request's held track gets its recording from the album tick's checked fill (`recording_filled`, homelab#2589).

```bash

kubectl exec -n <ns> deploy/music-pipeline -- music-mb-fingerprint --recheck              # dry run: the whole library
kubectl exec -n <ns> deploy/music-pipeline -- music-mb-fingerprint --recheck --apply      # replace the flagged guesses
kubectl exec -n <ns> deploy/music-pipeline -- music-mb-fingerprint --recheck --run-id r1  # a recorded dry run; the same command continues it
kubectl exec -n <ns> deploy/music-pipeline -- music-mb-fingerprint --replace-run r1       # what applying run r1 would do now

kubectl exec -n <ns> deploy/music-pipeline -- music-mb-fingerprint --refresh-replaced                      # dry run: title and trackdisambig of every replaced item

kubectl exec -n <ns> deploy/music-pipeline -- music-mb-fingerprint --candidates 13744    # read-only: the recordings it could be
```

**A recording set by hand (homelab#2583):** some audio's AcoustID fingerprint is linked to a sibling recording (4230, *Bye*, to "Bye (Rough Mix 2)", whose title reads as the same song), so the recheck can't fix the item and would put the wrong recording back. `--set-recording <item ID> <recording MBID>` (the MCP's `set_recording`) sets it by hand. It looks the recording up on MusicBrainz and prints `[SETREC] <id> — <title> (<artist>, <length>): mb_trackid <old> → <new>, '<recording title>' by <credit> (<length>)`, the `title` and `trackdisambig` changes that go with it (the recheck's refresh, above), and `[SUSPECT]` when the recording's title names another song than the item's. A recording MusicBrainz doesn't have, or a failed lookup, is refused with nothing changed. `--apply` stores it under the pipeline lock with a `recording_set` event (migration 17; `data.old`, `data.new`, `data.refreshed`) in the same transaction, sets the flexible field `recording_set` to the recording, and writes the file's tags, so a later `beet update` reads the same ID back. Don't use `beet modify -W` for it: that changes the database only, the file keeps the old ID, and every scan's `beet update` reads a file's tags back whenever the file is newer than its row, which a database-only change always makes it: beets resets an item's stored mtime to 0 whenever a tag field changes (homelab#2723). On 2026-11-02 such an edit of 4230 was gone by the next check, with no event either way. The recheck skips an item while its `mb_trackid` is its `recording_set` (`[SUMMARY]` counts it as set by hand), and a recorded run's apply skips it too.

The IDs that go with the recording are aligned too (homelab#2623). These are the item's `isrc` (`;`-joined) and its `mb_releasetrackid`, each logged with why (`[ISRC] …`, `[RELEASETRACK] …`), shown before → after in the dry run and kept in `data.refreshed`.

- **ISRC.** One the recording has stays. One MusicBrainz gives only to other recordings goes: the guessed sibling's, or the file's own when the store tagged it with another take's (17061 carried the live take's `USSM12503412`). One MusicBrainz doesn't know stays, since it may be Spotify's. When the item then holds none of the recording's ISRCs and the recording has exactly one, that one is added. A recording with several is never guessed between.
- **`mb_releasetrackid`.** It becomes the track of the item's release (`mb_albumid`) that holds the recording, the one at the item's position when the recording appears more than once. Otherwise it is cleared.
- **Playlist slots.** An ISRC that goes is checked against the playlist stores. The call is refused, with nothing changed, when an entry resolves to this item by that ISRC alone, since its slot would go empty. It is also refused when the stores can't be read (no music database).

**Which recording an item is (homelab#2623):** `music-mb-fingerprint --candidates <item ID>` (the MCP's `recording_candidates`, read-only) is for a wrong recording that AcoustID agrees with. A remaster and its 5.1 fold-down or live take fingerprint alike, so the release the item sits on settles it.

- It reads the item's release (`mb_albumid`, `inc=recordings+isrcs`) and lists `[AT-POSITION]`, the recording at its disc and track (with no disc number, the track counts across the release), and `[SAME-TITLE]`, every other recording of the same song, version notes dropped.
- Each line has the MBID, title, disambiguation, length (and how far it is from the file's), positions and ISRCs, with `← current` on the one the item holds.
- When the item's disc or track isn't on its release (`[VARIANT]`, as for *Nebraska '82*, whose variants order their discs differently), it also reads up to three releases of the group that fit the item's disc layout, digital first, and lists their recordings at its position and of the same song.
- It never decides: pick one with the user, then `--set-recording`.

**`mb_releasetrackid` held the recording ID (homelab#2623).** beets 2.14's `TrackInfo` maps `release_track_id or track_id` to `mb_releasetrackid`, and a singleton match has no release track, so every import stored its recording ID there. The value names no release track, and it goes stale once the recording is replaced (13744, 3809 and 17061 all had `mb_releasetrackid == mb_trackid`). The plugin now clears it at `import_task_apply` when it equals `mb_trackid` (`clear_singleton_release_track`, after the file-title restore). Items imported before that keep it until a `set_recording` aligns it.

**A recorded recheck (homelab#2553):** a whole-library run takes about an hour, so `--recheck --run-id <id>` records it in the music database (migration 12): a `long_runs` row with its checkpoint (items walked, the last item ID, the counts so far) every 25 items, and its findings in `recheck_findings` (each flagged item's guess, its recordings, the one replacement if there is one, and its file's path, size and mtime at the lookup). It walks the items in ID order. Started again with the same ID (and the same item IDs, if any), it continues after its checkpoint with `[RESUME] run <id>: continuing after item N (P of T walked, F flagged so far)`, so a killed run loses at most 25 lookups. A run that stopped on failed lookups is `failed` and continues the same way; a finished one is never re-run (start a new ID). One process at a time holds a run (a Postgres advisory lock); a second is refused. A recorded run is always a dry run. `--replace-run <id>` reads its findings, never AcoustID, and lists for each replaceable item what an apply does as the library stands now: `[WOULD-REPLACE]`, `[SKIP] <id>: <why>` (gone, its `mb_trackid` changed, or its file changed since the check: `replace_item` swaps the audio and keeps `mb_trackid`, so the ID alone can't tell; recheck such an item by ID), or `[DONE]` (it holds the replacement already). `--replace-run <id> --apply` does it under the pipeline lock, each replacement with its `recording_replaced` event (`data.run` names the run) and the finding's outcome in one transaction. It refreshes each replaced item's `title` and `trackdisambig` as above (the dry run makes no MusicBrainz call, so it lists only the replacements), and its `[SUMMARY]` counts the items refreshed and those whose lookup failed. An interrupted apply is finished by running it again: every item is checked again, and one that holds its replacement already has its tags written again (and its event recorded, if the kill came before it). The apply refuses a run that isn't finished or finished more than 7 days ago; the nightly prunes runs 30 days after they finish. The plain `--recheck` (no run ID) is as before, except that its `--apply` also skips an item whose file changed since its lookup.

**Titles of the wrong version (homelab#2544):** beets' singleton match writes the closest MusicBrainz recording's `title` and `trackdisambig` over the file's, and the closest can be a sibling: a stereo album track titled *(5.1 mix)*, a studio track with `trackdisambig` "live, 1992‐05‐28: …". `music-audit-titles` lists the items whose `title` or `trackdisambig` names a version (`5.1`, `live`, `demo`, `alternate` (also `alt`, `alternative`), `mono`, `take`, `outtake`; whole words, any case) that Spotify's entry at the item's slot doesn't: the playlist-store record for one of its Spotify IDs, the one on its `spotify_album_id` first, else canon's preference. A word in the title counts when it appears more often than in Spotify's title, so a song whose name holds it (*Live Forever*, *Take Five*) is not flagged; a word in `trackdisambig` counts when Spotify's version part (after ` - ` or in brackets) lacks it. Words only Spotify's title names are never flagged, and a word in Spotify's album name counts as Spotify's (a live album's tracks are often titled bare). Grouped by album (sorted by album, then disc and track), each `[VERSION]` line gives the item ID, its position, our title and `trackdisambig`, Spotify's title and the differing words, and each album with a record its `music-album-reset … --reimport` command: the fix is the album's. Items with no Spotify ID, or whose IDs no store describes, are counted, not compared. It can't see a wrong title with no version word in it (a different song under the slot's version notes), and a song whose name holds a version word only on our side (Spotify spelling it otherwise) shows as a false positive. Read-only: the library and the stores, no Spotify or MusicBrainz call. The Music MCP runs it as `audit_titles`.
```bash
kubectl exec -n <ns> deploy/music-pipeline -- music-audit-titles
```

**Canonical albums (#209):** Spotify decides album grouping. An item with a Spotify ID takes `album`, `albumartist`, the release date and its track/disc numbering from the Spotify album its playlist entry is on (an `album` release over a `single` or `compilation`, then one a playlist names today, then the earliest), and beets moves the file. A track on a `single` moves to a standard album by the same album artist holding the same recording (an EP, which Spotify files as `single`, only when the track is already filed under it), found by ISRC with a Spotify track search (cached in the `canon-isrc` document, one search a second, 20 per scan; a track still waiting for its search is marked `canon_wait` and picked up by the next scan). Its cover follows when the album name or album artist changes, or when the file has none. An item whose move would land on another file's path is left as it is (`[CLASH]`, a duplicate for #210); an album record's item is tagged in place instead (#306). A path that differs from another library item's only in case (or Unicode form) is a clash too (homelab#2742: `[CLASH] … item <id> has <path>, which differs from it only in case`), checked against every item's path, not only those canonicalised; a move that changes only the item's own case goes ahead. Spotify sometimes lists one album twice (#214): releases of the same type with the same album artist and name form a twin group whose representative (most playlist entries, then the earliest, then the most tracks) takes every item once its recording is known to be on it, by a playlist entry's ISRC or the same ISRC search (`[TWIN]` lines in the dry run; `[NOTWIN]` when the search shows the recording only on the other release, as for two self-titled albums). A change to beets-only fields (`spotify_album_id`, `mb_album_via`) updates the database without rewriting the file. Navidrome groups by the MusicBrainz album ID first, so the album-level MusicBrainz tags follow too: the release MusicBrainz links to the Spotify album URL, else one holding the album's ISRCs with its track count and title, else one with its barcode (one Spotify album call), else they are cleared (`[MB-NONE]`, with a Harmony link to add the release to MusicBrainz). Track-level IDs and ISRCs stay. Lookups are cached in the `mb-releases` document; each scan resolves up to 20 albums and leaves the rest `mb_album_via=pending` for the next, and misses are retried weekly. A Usenet release is the album (#266, #279): an item stamped `album_record` takes its record's Spotify album (album, album artist, date, cover, `spotify_album_id`) and the MusicBrainz album tags of the release its files are (`mb_album_via=files`), and keeps the release's own disc/track, whatever its Spotify track IDs say or whether it has any; a `.album` playlist lists those items alone, in disc/track order. Older release items keep #278's rule: on their album record's album when one of their IDs is (`[HOME]`). Album tracks get Spotify IDs only from an ISRC, or from disc/track and title together, never from a title alone (homelab#2664: `music_scan.identity.number_match`). A disc of 0 counts as disc 1, and `tracktotal` isn't asked. A renumbered track finds another title at its slot and gets no ID; neither does a version only one side names, or a track whose ISRCs disagree with the entry's, unless MusicBrainz lists both on the item's recording or the item's recording is a surround mix and the file has two channels (a CD rip that took the Dolby Atmos mix's ISRC from beets' guess). A clean and an explicit recording can't be told apart by length or AcoustID, so that entry stays empty. A link the release's numbering doesn't back only fills an entry no library item holds, and its ID also goes in `words_ids`, so it never supersedes. Each track left without an ID logs `[NUMBER]` or `[NOID]` and is in the `id_linked` event's `skipped`. On a later playlist of the album, title words give the source only, and the same rungs decide the ID. **The album copy supersedes loose copies that predate it** (`music_scan.supersede`): a non-Usenet item with the same Spotify ID, ISRC or MusicBrainz recording ID as one of the release's items, or at the slot of a release item with no Spotify ID on the same Spotify album when the release has Spotify's track count, is merged into the album item (`[SUPERSEDE]`). A loose item canon moved onto the album from a twin release holds the twin's Spotify ID, so the album's tracklist resolves it (#274): the entry with its ISRC, else the entry at its disc/track (vetoed by disjoint ISRCs), and the album item holding that entry's Spotify ID replaces it. The album item takes its playlists, IDs and `mb_trackid` (so Navidrome keeps plays and stars), its file goes to `quarantine/replaced/`, the album item moves to the freed path when it sat beside it as a `.1` copy (`[MOVE]`), and the `.m3u` files are regenerated. A Spotify ID from the title rung never supersedes. A loose item on the album that matches nothing is kept and listed as `[KEEP]` with the reason (no Spotify ID, no tracklist, its track held by no release item or only by title words, no entry at its slot, disjoint ISRCs) for `music-audit-dupes`, in a dry run (an apply logs it at DEBUG, and an import only counts them); a manual import is never replaced (`[MANUAL]`). The duplicate hook imports a Usenet track whose same-recording duplicates are all spotdl items (`[ALBUM]`) so that the supersede can run. Canon runs at every scan and after each Usenet album import; supersede runs only after a Usenet album import (on that release's items) and from `music-canon-albums`, never at a scan. `music-canon-albums` backfills, supersedes included, the library from the playlist pages (cached for a day, so the `--apply` after a dry run reads Spotify once):
```bash
kubectl exec -n <ns> deploy/music-pipeline -- music-canon-albums           # dry run: [ALBUM]/[RETAG] lines and totals
kubectl exec -n <ns> deploy/music-pipeline -- music-canon-albums --apply   # retag, move, regenerate the .m3u files (#218), then rescan Navidrome
```
The dry run still looks albums up on MusicBrainz (about 1–6 s each) and caches the results. `--mb-budget N` caps the lookups per run. The dry run also runs the single → album ISRC searches (one a second, cached for the `--apply`); `--search-budget N` caps them.

**Recover after PVC loss:**
1. Restore `beets-data` PVC from backup (restores `library.db`).
2. The state (album store, playlist stores, backoff, caches) is in the `music` database, which the PVC doesn't hold: restore it from its own backup only if the database was lost too. A fetch rebuilds every playlist store from Spotify and downloads only what the restored library lacks; local-only entries (none so far) are lost with the stores.

## Notes and gotchas

- **Track identity.** `spotify_ids` (comma-separated Spotify track IDs: one recording has different IDs on the single, the album and compilations) and `isrc` (`;`-separated, MusicBrainz's plus Spotify's) decide whether a playlist entry is a library item: Spotify ID, then ISRC, then MusicBrainz recording ID, and title+artist only as a logged last resort (`[WORDS]`, whole titles: a remaster is another track, #252). The title+artist resort only reaches items with no Spotify ID (#257): an item that has one is that track, so a same-title entry with another ID never takes it (the slots, `.m3u` regen, and a removal's title fallback alike). Two recordings are one track only when one of those identifiers agrees (#255): the duplicate hook merges an incoming track only on a shared Spotify ID, ISRC or recording ID (`[SAME]`; a recording ID only with lengths within 2s, homelab#2540), and a same-title track imports as its own item, `[SPLIT]` when the ISRCs differ and `[APART]` when one side has none. Real duplicates that arrive without IDs are found by `music-audit-dupes` (fingerprints).
- **`sources` is provenance, not membership.** A track imported or linked by several playlists carries all their names (e.g. `sources=playlist-a,playlist-b`), and keeps them after it leaves a playlist. What a playlist lists is its store's alone (homelab#1914).
- **Playlist slots (#228).** Each playlist entry is a slot that every scan fills by resolving it against the whole library by Spotify ID, then ISRC (`[SLOT] <playlist>: N entr(ies) filled from the library by ID/ISRC`, per track at debug), never by recording anything. So a track that arrived by any route (a Usenet album, another playlist's download, a manual import or replacement) is listed by every playlist that names it at the next scan, with no download and no tag write. The album hooks' `missing` and `have` read the same resolution. The scan pushes `music_playlist_slots_empty{playlist}` (entries with no item: on a spotdl playlist, tracks still waiting for a download).
- **`beet update` does not prune deleted files.** Use `beet remove <query>` with a specific query. Never run `beet remove` without a query.
- **Cookies expire.** Re-export from browser when downloads fail at quality.
- **Spotify rate limits.** Always use your own app credentials — the spotdl defaults are shared and hit limits quickly. For large playlists, set `SYNC_TRACK_LIMIT` to cap new downloads per session (e.g. `50`); the pipeline picks up where it left off each run. The budget is spent on one want list across playlists in `playlists.conf` order (new entries the library lacks, minus backoff); once spent, the remaining playlists are still fetched, `[HAVE]`-linked and diffed for removals, and only their downloads wait (counted in the `Track budget` line), so no playlist goes unchecked (#228).
- **Long Spotify rate limits fail the run.** A 429 whose `Retry-After` exceeds 120s is not slept through (it once said 17.5h): the run fails with `Spotify rate-limited: Retry-After <n>s, until <UTC>`, the end goes to the `spotify-rate-limit` document in the `music` database and to the `music_spotify_rate_limited_until_seconds` gauge (Pushgateway job `music_spotify`), and every Spotify reader fails without calling Spotify until then. Shorter ones are waited out.
- **MusicBrainz threshold.** `strong_rec_thresh: 0.10` in `config/beets/config.yaml`. Tracks that don't match confidently land in quarantine. A second `--asis` pass then imports any quarantined file that already has sufficient embedded tags (title, artist, album, tracknumber); the rest stay in quarantine for manual review. Raise the threshold if too many valid tracks are being quarantined.
- **The playlist store (homelab#1914) is the playlist state.** One row per playlist in the `music` database's `playlist_stores` ([State](#state)), holding every entry in Spotify's order with the full song record, then its local entries (library items on the playlist that are not on Spotify; none so far). "Downloaded" is the entry resolving to a library item by Spotify ID or ISRC, never recorded. The nightly rewrites a spotdl playlist's store from Spotify and downloads its want list: entries no library item holds, minus downloads waiting in the inbox or quarantine (never fetched again, #165) and backoff. The sync logs one summary line per playlist (tracks on Spotify, held or waiting, wanted split into on-the-playlist-before and new, removed) and one `[BACK]` count; only a track acted on (`[OK]`, `[MISS]`, `[FAIL]`, `[HAVE]`, `[PIN]`) gets its own line (#320). The album tick writes an `album` playlist's; a `nosync` playlist's is built from Spotify once and kept. A track removed on Spotify leaves the store and the `.m3u`; its file stays in the library (soft delete). Every store write that changes membership records it (homelab#2361, migration 22): a `playlist_entry_added` or `playlist_entry_removed` event per entry that joined or left, logged `[STORE] <playlist>: +|- <artist> — <title> (<by>)`, in the same transaction as the write, with `data.playlist`, `data.by` (`spotify` for a fetch, `regen` for a local entry the scan dropped once its Spotify entry held it) and the entry's identity (`key`, `song_id`, `isrc`, `url`, or a local entry's `item_id` and `path`). A reorder or a richer record is no change. A store's first write, and a write changing more than 100 entries, records one event per kind instead (`data.count`, `data.created` or `data.bulk`, the first 20 `data.entries`). `find_events` with those kinds shows what changed a playlist and when. Whether a spotdl copy is an album's top-up is the store's answer too (`release._topup`). The stores replaced `.spotdl`, the unlink queue and `reconcile` (stage c); old `.spotdl` files left on the PVC are no longer read.

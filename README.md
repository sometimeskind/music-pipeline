# music-pipeline

Dockerized music pipeline: Spotify playlists → spotdl downloads → beets import/tag → music library.

```
Spotify playlists → spotdl → beets → ~/Music/library
```

A single long-running service container orchestrates everything via Prefect. Two flows run on configurable schedules:

| Flow | Default schedule | Does |
|---|---|---|
| `music-fetch` | Daily 03:00 UTC (`FETCH_CRON`) | Spotify/YouTube sync — downloads new tracks, queues removals |
| `music-scan` | On demand (file watcher or HTTP API) | Import inbox → beets, refresh metadata, regenerate .m3u |

---

## Pipeline internals

A full sync cycle (`music-ingest` followed by `music-scan`) runs 8 discrete steps. Steps 1–2 are the **fetch phase**; steps 3–8 are the **scan phase**.

```
┌─ FETCH PHASE (music-ingest) ──────────────────────────────────────────┐
│                                                                        │
│  [1] Playlist reconciliation                                           │
│        Reads playlists.conf; creates new playlists' inbox dirs, syncs  │
│        .nosync/.album sentinels, deletes the store and .m3u of a      │
│        playlist removed from config, then the Navidrome playlist       │
│        imported from any .m3u that is gone.                            │
│        │                                                               │
│        ▼                                                               │
│  [2] spotdl sync                                                       │
│        Fetches each playlist from Spotify, writes its playlist store   │
│        and downloads its want list (tracks no library item holds)     │
│        into inbox/. A track removed on Spotify leaves the store.      │
│                                                                        │
└────────────────────────────────────────┬───────────────────────────────┘
                                         │
┌─ SCAN PHASE (music-scan) ─────────────▼───────────────────────────────┐
│                                                                        │
│  [3] Length guard (LENGTH_GUARD)                                       │
│        Checks each spotdl download against the Spotify duration (±10%) │
│        and for mid-track silence; moves wrong audio to                 │
│        quarantine/rejected/ (asis pass skips it, no re-download).      │
│        │                                                               │
│        ▼                                                               │
│  [4] Beets import                                                      │
│        Matches inbox audio to MusicBrainz/AcoustID; moves matched      │
│        files to library/. Low-confidence matches go to quarantine/.    │
│        │                                                               │
│        ▼                                                               │
│  [5] Quarantine + asis pass                                            │
│        Moves unmatched inbox leftovers to quarantine/. Then attempts   │
│        a second beet import --asis for quarantine files that already   │
│        have sufficient embedded tags (title, artist, album, track#).   │
│        │                                                               │
│        ▼                                                               │
│  [6] Library metadata refresh                                          │
│        Runs beet update to refresh metadata on existing library items. │
│        │                                                               │
│        ▼                                                               │
│  [7] Playlist generation                                               │
│        Regenerates each .m3u from its playlist store (in Spotify       │
│        playlist order), resolving entries against the library.         │
│        │                                                               │
│        ▼                                                               │
│  [8] Navidrome trigger                                                 │
│        Calls the Navidrome Subsonic API to trigger a library rescan.   │
│                                                                        │
└────────────────────────────────────────────────────────────────────────┘
```

The scan phase is idempotent and safe to run at any time: on its 5-minute schedule with no preceding fetch it only imports what arrived and rewrites the `.m3u` files.

## State

The pipeline's own state is in the Postgres database `music` (`MUSIC_DATABASE_URL`, homelab#2410), read and written through one module, `music_fetch.state` (migration 4 in `music_fetch/db.py`; the overrides are migration 5 and `music_fetch.overrides`, the album requests migration 7 and `music_fetch.album_requests`, the Later queue migration 8 and `music_fetch.later_queue`):

| Table | Holds | Was |
|---|---|---|
| `albums`, `album_refs`, `album_playlists`, `indexer_use` | The album store: each album's status, release blocklist, Spotify snapshot per album playlist, fallback tracklist; the indexer budget | `inbox/spotdl/.albums.json` |
| `playlist_stores` | The playlist stores, one row per playlist | `inbox/spotdl/.store/<name>.json` |
| `spotdl_failures` | The spotdl backoff | `inbox/.spotdl-failures.json` (on the scratch volume, so a restore forgot it) |
| `kv` | The MusicBrainz release and ISRC caches (`mb-releases`, `canon-isrc`), the playlist-page cache (`canon-pages`), the Spotify rate-limit stamp, the empty-slots report, and the `state-imported` (historical) and `overrides-imported` markers | `.mb-releases.json`, `.canon-isrc.json`, `.canon-pages.json`, `.spotify-rate-limit.json`, `.empty-slots.json` |
| `album_overrides`, `track_pins` | Search overrides and holds (on an album row), track pins (by Spotify track ID), each with its reason, `set_by` and `set_at` (homelab#2484, see Album mode) | homelab's ConfigMap: `album-overrides.conf`, `track-pins.conf` |
| `album_requests` | Albums requested by MusicBrainz release group: the preferred release, the tracklist read from MusicBrainz, `requested_by` and `requested_at` (homelab#2478, see Album requests below) | new |
| `later_queue` | The Later queue: one row per album by release group, `added_at`, and `available_at` (when the library first held it whole; the `.m3u` order) (homelab#2478, see The Later queue below) | the `later` Spotify playlist, until the stage 3 cutover |

beets' library stays SQLite (`library.db`): beets has no other backend. The events (homelab#2413) are in the same database.

**The database is the only copy.** `music-state-import` moved the JSON dot files in on 2026-10-29 (homelab#2410). They were kept, unwritten, as a rollback copy behind a switch file (`inbox/spotdl/.state-in-db`) for one release; after it the JSON code, the switch and the import were removed and the files deleted (homelab#2502). A new piece of state is a migration and a `music_fetch.state` accessor, never a file. The tests run on Postgres too (CLAUDE.md, Testing).

**Album keys.** An album row is keyed by its MusicBrainz release group (homelab#2478). A row whose release group isn't known yet has none, and an `unresolved` flag says why: `pending` (not looked up), `no-match`, `conflict` (the evidence disagrees) or `in-flight` (a merge waits for an import to finish). Each of an album's Spotify album IDs, or a local album's `artist/name`, is a ref in `album_refs`, so two Spotify editions of one release group are one row. An override or hold is on the row itself, and follows it by ref through a merge (homelab#2484).

**The album key** is what album mode, the Music MCP and the `album_record` beets stamp on each imported item name an album by. It is the album's row id (homelab#2478): opaque, and the same before and after the album resolves to a release group, so resolving moves no stamp. Never read a key for what it is: a Spotify album ID is the record's `spotify_album_ids` (`state.primary_spotify`). Until the operator's one-time `music-album-rekey --apply` (the `album-keys` kv marker) the key is the old scheme, the primary Spotify album ID (else the release group, else the name), and a record not saved yet is keyed that way until its first save gives it a row.
- `music-album-rekey` (dry run unless `--apply`) lists the items whose stamp moves, per album. `--apply`, under the `albums` and `pipeline` locks, copies `library.db` to `library.db.pre-rekey-<UTC time>` beside it, writes the marker, then restamps every item (beets' database only, in one transaction). `--revert --apply` moves the stamps back to the old keys and then removes the marker: run it before rolling the image back to one from before homelab#2478, which reads stamps as Spotify album IDs.
- **A row that goes** (a merge's loser, an album that left its playlists) leaves its refs in `album_rows_gone`. Every scan, before its canon, moves a stamp naming a gone row (or an old key, or another edition's Spotify ID) to the record that holds one of its refs now (`[RESTAMP] artist — album: N item(s) old → new`, `music_scan.restamp`); a stamp no record claims is left as it is. Only once the keys are row ids: before that, the stamps are the operator's to move.

**The resolver** (`music_fetch.resolve`) keys the rows it can, every album tick and in `music-album-resolve` (dry run unless `--apply`). The first evidence that answers wins, never a fuzzy match:
1. the release group of the release album mode imported for the album (what is on disk); evidence that disagrees with it is reported;
2. the `mb-releases` cache's release for its Spotify album (by URL, ISRC or barcode, the canon lookups);
3. the beets items tagged with its Spotify album ID, when every one that has a release group has the same one.

Cache and library evidence that name two release groups leave the row `conflict`. Two rows that resolve to one release group merge (`[MERGE]`), never while either is grabbed or importing (they wait `in-flight`): the survivor is the row that already had the release group, else the one furthest along, and it takes the others' Spotify IDs, playlist tracks and blocklisted releases, the higher attempt count and the strongest origin. Each pass that changes anything logs `[REKEY]`, `[MERGE]`, `[CONFLICT]` and `[FLAG]` lines and a `Resolve:` summary.

**Album requests** (homelab#2478). `music-requests add [--apply] -- <release group>[=<preferred release>]…` (the Music MCP's `request_album`) asks for whole albums by MusicBrainz release group, each an MBID or a musicbrainz.org URL; `music-requests list [--status S]` (`list_requests`) shows each request with its album's status, `pending` until the tick has queued it. The dry run reads each tracklist from MusicBrainz: the preferred release's, else the earliest official release with the release group's most common track count (releases marked live left out, unless the group is a live album; video media left out), stored as album mode's track entries without Spotify IDs. Each album tick (`albums.feed_requests`, logged `[REQUESTS]`) gives every request an album row with origin `request` and those tracks under the pseudo-playlist `request`, or upgrades the row that has the release group: a waiting wants or library row becomes the request's (the whole album wanted), and an album playlist's row is marked `requested`, so it stays when it leaves its playlists and then takes the request's tracks. A playlist's Spotify tracks always stand in for the request's, so `have` and the import read one tracklist. A request is searched with the album playlists' albums, ahead of the fed ones, and imported under `inbox/usenet/request/`. When Usenet misses or all its releases fail, it falls back to spotdl from MusicBrainz (`albums.fallbacks`): the tick reads the request's tracklist release once (`album_requests.release_songs`, from the same 10 reads a tick as Spotify tracklists) as spotdl songs with every field set, so spotdl never asks Spotify. Each song's ID is its MusicBrainz recording and its URL `https://musicbrainz.org/recording/<id>`, with the release's Cover Art Archive front as its cover. spotdl finds it on YouTube Music by its ISRC, else by artists, title and length. Each credited artist is its own name in the song's artists (a track with no credit of its own takes the release's), and when that search finds nothing for a credit naming several artists, it is searched once more by the first credited artist alone, its ISRC already tried (homelab#2533, `[ALONE]`): spotdl joins every artist into its query and scores results by all of them, so a joint credit often finds nothing. Only the search widens: the song keeps its full credit and the same acceptance check. The nightly downloads the tracks no item stamped with the album's key holds into `unverified/request/`, outside the inbox, under the same budget and backoff. Before the import, the scan's `guard.verify_requests` checks each file: the length guard's length and silence checks against MusicBrainz's length, then an AcoustID lookup of its fingerprint (`ACOUSTID_APIKEY`). Only a file AcoustID names as the track's own recording (score 0.85 or more) moves to `inbox/spotdl/request/` (`[VERIFIED]`). Every other file goes to `quarantine/rejected/request/` with its reason (`music_scan_rejected_tracks_total{reason}`), whatever `LENGTH_GUARD` says: `duration` or `silence`; `fingerprint` when AcoustID names other recordings (or ours below 0.85), or the file can't be fingerprinted; `acoustid-unknown` when AcoustID has no MusicBrainz recording for the audio at all, no result or only results with no recording (homelab#2546). A `fingerprint` reject is the wrong audio; an `acoustid-unknown` one may be right, from a new or obscure release AcoustID hasn't linked yet, but it is rejected all the same. Its URL is then held, so it isn't downloaded again, and the track stays a gap. A failed lookup (an AcoustID error, or no answer in 30s) is neither: it leaves the file for the next scan. The beets plugin records the verified recording as `fallback_recording` (and `mb_trackid` when beets set none), never as a Spotify field. A copy the library already holds of that recording doesn't stop it importing (`[BOTH]`), since the album keeps its own copies. Before canon, every scan stamps such an item with its request's key (`release.claim_fallback`, `[CLAIM]`). Canon names a request's items from MusicBrainz: album, album artist and date from the record, `mb_albumid`/`mb_releasegroupid`/`mb_albumartistid` from the tracklist release (`mb_album_via=request`), or from the files' own release for a Usenet import (`files`), and a fallback track's disc/track from the tracklist. They are one album with no `spotify_album_id`. The album is `filled` once its stamped items hold every recording, and until then `list_requests` shows `fallback_left` and `digest_summary` lists it under `requests.fallback`. Both also show `fallback_rejected`, the tracks left whose download is held in `quarantine/rejected/request/`, by reason (read from each file's `.reason` sidecar), and `acoustid_unknown_only` when every one of them is `acoustid-unknown`: the operator decides what such an album needs (Usenet only, a manual source, or a later retry once AcoustID knows the release). Rejects from before homelab#2546 all read `fingerprint`. While it has gaps it is searched on Usenet again every 7 days (`MISSING_RETRY`, as a miss is; it stays `fallback` on a miss). A release grabbed then is the album, and retires the spotdl copies whose recordings it holds. `music-requests fallback-sample [--n=10] [--seed=0]` (exec, an operator step) measures the hit rate: it runs these steps on N albums the library holds whole into a scratch directory and keeps nothing. Per album and in total, it reports the tracks spotdl found and the ones AcoustID accepted or rejected (by reason, `fingerprint` and `acoustid-unknown` apart), and how many of each match the library's own copy by fingerprint, the `acoustid-unknown` rejects on their own too. Before this fallback, a request that missed stayed `missing` (searched again weekly). Rolling back to an image from before migration 7 leaves the request rows alone, but that image would treat a request row as an album playlist's and fall it back to spotdl with no tracks to fetch, marking it `filled`: reset those albums after rolling forward again.

`music-requests search [--limit=N] -- <query>` (`search_releases`) finds the release group to request: it sends the typed query to MusicBrainz's release-group search as given (never a library title from an agent), and lists the best N matches (default 5, at most 10), each with its types, year and releases (date, country, media, track count), flagging live, remix, compilation, demo, DJ-mix and mixtape release groups and releases that are not official or whose disambiguation says live, demo, remix or compilation.

**The Later queue** (homelab#2478). `music-requests add --later` (`request_album` with `later`) also appends the albums to Later, in the order given; an album requested already is only appended. `music-later list` (`get_later`) shows the queue, and `music-later remove [--apply] [--through=N] [--album=<album>]… -- <release group>…` (`remove_from_later`) takes albums off it, by release group, by album (`--album`, as `music-overrides` names one: its key, a Spotify album ID or URL, or `artist — album`; a query matching several albums is refused and lists them; homelab#2534) or Later's first N; their files stay in the library. An album's `available_at` is set when it is added if the library holds it whole (its row `have`, `imported` or `filled`), else by the first `.m3u` regen that finds it so (`[LATER] N album(s) now held whole`), which follows its import. A reset or reimport doesn't move it. `later.m3u` lists the available albums in `available_at` order, each album's stamped release (`album_record`, found without a Spotify album for a request's row) in disc/track order, so an album that arrives late joins the end. Pending albums aren't in it. The queue alone writes `later.m3u`: a playlist store named `later` is not read for it (the album playlist left `playlists.conf` at the stage 3 cutover). When the queue can't be read, `later.m3u` keeps its last content. Rolling back to an image from before migration 8 leaves the queue's rows alone and drops the queue's albums from `later.m3u` until rolling forward again. An image from before migration 9 leaves the entries queued by ref out of `later.m3u` (it logs each as having no album row).

**Automatic requests for Later** (homelab#2535, `music_fetch.later_requests`). Since the cutover `later` is no album playlist, so spotdl gets no fallback for its albums, and the MusicBrainz-built fallback covers requests only. Each album tick in `on` therefore first requests every Later album that isn't held whole (its row not `have`, `imported` or `filled`), has a release group and has no request yet, in queue order and at most 5 a tick (two or three MusicBrainz reads each): an ordinary request with `requested_by` `auto:later`, logged `[LATER] … requested automatically` and recorded as its `album_requested` event, which the same tick then feeds. Both tables are unique on release group, so an album is requested once: a partial fallback stays `fallback` and is searched again weekly, never requested again, and leaving Later doesn't withdraw the request. An entry queued by ref waits until a regen gives it its row's release group. A release group MusicBrainz gives no tracklist for is skipped for 7 days, each refusal a `failure` event (`data.what` `later_request`); a MusicBrainz outage stops the tick's requests until the next tick. One `[LATER-REQ]` line a tick counts them (`dry-run` mode only counts). `music-later auto-requests` lists what the next tick would request, read-only and without MusicBrainz. A request's row that is not held whole drops the tracks of playlists that left `playlists.conf` (the former `later` and `keep` rows' Spotify tracklists, which spotdl no longer reads), so the request's MusicBrainz tracklist and fallback take over (`[REQUESTS] … off later, which left playlists.conf`); a held row keeps its Spotify tracklist.

**The cutover** (homelab#2478 stage 3). `music-cutover` (dry run unless `--apply`) moves Later and Keep off Spotify once, while `later` and `keep` are still in `playlists.conf`: it reads their stores. Every album on the `later` store goes on the Later queue in the store's order, each a second before the next and before every entry the queue has, so it keeps its place ahead of the albums requested since; one on the queue already moves to its store place. Every album on the `keep` store becomes a request, its tracklist read from MusicBrainz by release group at `--apply` (one MusicBrainz can't answer for is listed as `[SKIP]`: run `--apply` again). An album whose row has no release group yet is listed (`[NO-RG]`): on Later it is queued in its place by its album ref instead (migration 9: `later_queue.ref`, its primary Spotify album ID, which follows the album through a merge), and each regen gives such an entry its row's release group once the row has one (`[LATER] … resolved to release group`; an entry the album has by release group already, from a request with `later` meanwhile, is merged into the earlier of the two). Until then `music-later remove` reaches it by `--album` or `--through`, not by release group. A Keep album with no release group gets no request, and its row stays as it is. A store album no row holds is listed (`[NO-ROW]`) and left out. The dry run renders `later.m3u` as the queue will write it and compares it with the file the last scan wrote: `later.m3u: unchanged by the cutover` is what to expect. `--apply` writes the queue entries (`later_added`, source `cutover`), the requests (`requested_by` `cutover:keep`) and the `later-keep-cutover` kv marker in one transaction, under the `albums` and `pipeline` locks; run again, it adds only what is missing. Then both lines leave `playlists.conf`, and the queue alone writes `later.m3u`. `music-cutover --revert --apply` takes off what the marker lists (the queue entries it added, each moved entry back to its place, the requests it added); after the lines have left `playlists.conf`, put them back first, so the stores are rebuilt at the next tick, and roll the image back to one from before the queue-only `later.m3u` (homelab#2478's cleanup), which merges the `later` store back into the file.

**Hand edits** (homelab#2503). `music-state` makes the edits the runbooks need, each a dry run unless `--apply`: `backoff` lists the spotdl backoff and `clear-backoff` empties it, so the next nightly retries every backed-off track (after new YouTube cookies; `just clear-failures-k8s`); `stores` lists the playlist stores with their Spotify and local entry counts, and `drop-store -- <playlist>` deletes one, so it is rebuilt from Spotify (a spotdl or `nosync` store at the next nightly, an album playlist's when its snapshot changes), saying how many local entries that loses; `clear-snapshot -- <playlist>` forgets an album playlist's Spotify snapshot, so the next album tick re-reads the playlist and writes its store. Each write waits for the locks of the flows that write the same rows, so a run in progress can't write its copy back over it: `pipeline` for the backoff, `albums` then `pipeline` for a store, `albums` (and the album store's save lock) for a snapshot. It records a `state_edited` event (migration 10, `data.what`: `backoff`, `store` or `snapshot`) in the same transaction.

**Postgres down.** The pipeline never runs without its state. Each run skips instead: the album tick logs `[DB-DOWN] Album tick skipped` and pushes `music_albums_last_tick_success 0`, the scan logs `[DB-DOWN] Scan skipped` (the inbox waits), and the nightly's preflight fails with `state_unavailable`. An album import triggered during the outage fails, and the tick's lost-trigger recovery imports it from SABnzbd history once the database is back.

## Setup

### 1. Clone and prepare

```bash
git clone https://github.com/sometimeskind/music-pipeline
cd music-pipeline
```

### 2. Export YouTube Premium cookies

spotdl requires YouTube Premium cookies for M4A 256 kbps quality.

**Each time cookies expire**, sign in to [music.youtube.com](https://music.youtube.com) in Firefox, then run:

```bash
just cookies
```

This extracts cookies directly from Firefox and saves them to `cookies.txt` (already in `.gitignore`).

Cookies expire every few weeks. Re-export when downloads start failing: the ingest run logs a `YouTube cookies ... look expired` warning, sets the `music_ingest_cookies_expired` gauge to 1, and records the per-track reason (e.g. `HTTP Error 403: Forbidden`) in the backoff (`music-state backoff`). After a re-export, `just clear-failures-k8s` empties the backoff so the next nightly retries every failed track.

Each ingest run also reads the expiry stated in `cookies.txt`: it logs `YouTube auth cookies expire <date>` and pushes the soonest expiry among the Google login cookies (`SID`, `HSID`, `SSID`, `APISID`, `SAPISID`, `__Secure-{1,3}PSID`, `__Secure-{1,3}PAPISID`, `LOGIN_INFO`) as `music_ingest_cookies_expiry_timestamp_seconds`. The homelab alert `MusicCookiesExpiringSoon` fires 7 days before that date. A file with no login cookies (exported signed out) logs a warning and pushes no expiry. The stated expiry is about a year out, and Google usually invalidates a session server-side before then, so `music_ingest_cookies_expired` stays the main signal.

### 3. Set up Spotify credentials

Store your Spotify Developer app credentials in 1Password:

- **Item:** `Personal/Spotify API`
- **Fields:** `username` (client ID), `credential` (client secret)

Create an `.env.tpl` for `op run`:

```bash
SPOTIFY_CLIENT_ID=op://Personal/Spotify API/username
SPOTIFY_CLIENT_SECRET=op://Personal/Spotify API/credential
```

### 4. Register playlists

Edit `config/playlists.conf` and add one line per playlist:

```
# name             spotify-url                                               [flags]
liked-songs        https://open.spotify.com/playlist/37i9dQZF1DXcBWIGoYBM5M
archived-mix       https://open.spotify.com/playlist/37i9dQZF1DXd9rLJfaAKCk  nosync
```

The optional `nosync` flag freezes a playlist: `music-ingest` creates a `.nosync` sentinel on the PVC and never syncs it from Spotify again. Its store is read from Spotify once and then kept, but its want list (the frozen entries no library item holds) is still downloaded every night, in store order and from the shared budget, until the playlist is complete. Each such run logs `[FROZEN-WANT] N track(s)` (homelab#2392). Frozen means the same list, not the same files: a frozen entry may resolve to another copy of the same recording, for example one an album import superseded. A frozen entry Spotify later replaced (a split or relinked track) stays an empty slot until it is fixed by hand. Remove the flag and run `music-ingest` again to unfreeze.

The optional `album` flag is for playlists that hold only whole albums. spotdl never syncs them (a `.album` sentinel). Instead, the `music-albums` flow downloads each album whole from Usenet through Prowlarr and SABnzbd. Every `ALBUM_POLL_SECONDS` it checks the playlist's Spotify `snapshot_id` and re-reads the tracks only when it has changed, so a playlist edit is picked up within one poll. Then it tops the SABnzbd queue up to `ALBUM_MAX_IN_FLIGHT` within a rolling-24h indexer budget. Its state (album status, release blocklist, indexer use) is the album store in the `music` database (see [State](#state)). Set `ALBUM_MODE=dry-run` first: it searches and logs `[PICK]` lines but never grabs.

**Album playlists sync at the album level (#268).** Spotify decides *which* albums are on the playlist; the local release decides *what is on* each album. An album is on the playlist while at least one of its tracks is, so adding one song on Spotify brings in the whole album: the album counts as `have` only when the library holds every playlist track and at least Spotify's track count of the album's tracks. The `.m3u` lists every local track of every album on the playlist (the items its entries resolve to, and every item canon filed on that Spotify album or, under the same name, on its #214 twin), album by album in playlist order, each in disc/track order, so a release's tracks without a Spotify ID are listed too. A track canon moved to another album (a single's track filed on its standard album) is listed alone. Removing one of an album's tracks on Spotify does nothing; when the last one goes, the tick logs `[GONE] <artist> — <album>: no track left on <playlist>`, and the album's lines leave the `.m3u` at the next regen. The tick writes the playlist's tracklist to its playlist store, as the nightly does for normal playlists. Normal playlists stay track level.

When SABnzbd finishes an album job, its post-processing script POSTs to `/trigger-album-import` (bearer `ALBUM_IMPORT_TOKEN`, which opens only that route). The `music-album-import` flow then:
1. moves the job into `inbox/usenet/<playlist>/`, so beets tags it `sources=<playlist>` and `via=usenet`;
2. runs the scan under the `pipeline` lock;
3. matches the release as a whole to a MusicBrainz release (beets' album matcher, without importing: `[RELEASE] <job> is <album> (<mbid>): N of its M track(s) have no file`, or `[NOMB]`), imports the files beets couldn't match as they are (`[REST]`), stamps the release's items `album_record=<album key>` and `release=<guid>`, and gives them Spotify track IDs as a best effort: by ISRC, then disc and track number when the title agrees (edition notes dropped, #278), never by title words alone;
4. judges the release (#279): **on album playlists the album is the unit, not its tracks.** The release is the album whatever its tracklist (another edition than Spotify's, missing or extra tracks, a file beets couldn't match): `[DONE] … N file(s) from <release>; K of Spotify's M titles not in this release`. Nothing of it is quarantined and nothing it lacks goes to spotdl. Its items take the album's tags from the record (canon, below), and every other copy of the album (an earlier release, items from before #279, spotdl's top-ups) whose recording the release holds moves to `quarantine/replaced/` (`[RETIRE]`). Two copies are one recording only when a Spotify track ID, an ISRC or a MusicBrainz recording ID agrees, never by title (#287). A copy whose recording the release lacks (a deluxe edition's bonus tracks, when the release is the standard edition) is the library's only copy: it stays on the album as a local-only extra (`[LOCAL]`), stamped `album_record` and `album_extra`, so canon files it under the album at the next scan and `music-album-audit-releases` no longer counts the album as mixed. A later release that holds its recording retires it, and so does the release itself once its recording IDs arrive (#294): retire runs before the release gets its Spotify IDs, so a release beets matched to nothing in MusicBrainz (`[NOMB]`) holds no recording yet and keeps every old copy as an extra. Right after the Spotify IDs, and in every scan before canon, an extra whose recording the album's release now holds moves to `quarantine/replaced/` too (`[RETIRE] … (extra, now held)`). An extra none of whose IDs the release holds, but whose audio one release item has (a legacy copy with no IDs, or a release beets matched to another MusicBrainz recording), would otherwise clash with that item at canon every scan (`[CLASH]`): when the pair is in `music-audit-dupes`'s certain tier (an AcoustID match, lengths within 2 s, the same title once edition suffixes are dropped), the extra is merged into the release item as `--apply` would (`[RETIRE] … (extra, same audio): merged into <id>`, then `[MERGE]`; its file to `quarantine/replaced/`), and the next canon files the release item on the canonical path (#301). An uncertain pair, or one whose audio two release items share, stays for the operator, and is surfaced (#306): an extra left on the album whose title, edition suffixes dropped, is a release track's is logged once, `[SAMETITLE] <id> <artist> — <title> [<album>] (<length>): the release's <id> (<length>) has its title, but no ID agrees`, and stamped `album_extra_twin`; `music-album-audit-releases` lists those albums after the mixed ones (`[SAMETITLE] <artist> — <album> (<id>): N local-only extra(s) …`), each pair with its `music-audit-dupes --merge` command (the keeper the release item, #311). The title only reports: nothing is merged, tagged or retired by it (track identity is by ID only). A release item whose canonical path such an extra holds is not left behind as a stray album: canon gives it the album's tags where it is (`[CLASH] <id> <path> → <dest>: … tagged in place`, stamped `canon_clash`), and every scan tries the move again until the path is free. Extras take the album's tags at canon, the kept release's `mb_albumid` included (`mb_album_via` `files`), although their files are not from that release: Navidrome groups by the MusicBrainz album ID, so an extra without it would show as an album of its own. Their recording IDs (`mb_trackid`, ISRC, Spotify IDs) stay their own, and `album_extra` marks them. Local-only extras never take a Spotify ID away from the release's own items. Two album records that resolve to one release group merge (`music_fetch.resolve`), and when both had imported, the survivor holds both releases once the scan restamps the absorbed record's items (homelab#2545). Every scan, after the restamp and before the extras above, keeps such a record's own release (its `best_copy` while it waits for a better copy, else the newest release whose import started by its `imported_at`; a merge keeps the survivor's) and retires the rest as an import would: `[MERGED] <artist> — <album> (<id>): keeps its own release <release> (N); retiring …`, then `[RETIRE]` and `[LOCAL]`. A record mid-import or reset for a reimport is left to its import, and one whose own release nothing tells is logged `[MULTI]` and left alone. `music-album-audit-releases --merged` lists those records and what the next scan retires of each, read-only.

A release fails only for a broken download, for being another album (`[WRONG]`: fewer than half of the album's Spotify titles, edition notes dropped, among its items; albums of fewer than 4 tracks aren't judged; its items go to `quarantine/replaced/`), or for lacking tracks of its own MusicBrainz release (`[INCOMPLETE]`). A failed release is blocklisted and the next one tried. An incomplete copy stays in the library until a more complete one has imported, and the next grab must be the same edition (the edition words in its title: deluxe, remaster, anniversary…); when no copy of that edition is left, or after 3 releases, the most complete copy is the album (`[DONE] … lacks N track(s) of its own release`). Searches prefer the Spotify album's edition, and take another edition when Usenet has none (`usenet.rank`). After 3 failed releases with no copy kept the album is `failed`, and the last release's quarantined files are kept for review. Usenet tracks never go through the scan's asis pass. A trigger that never arrives is recovered from SABnzbd history by the next tick, an hour after the grab. A failure that isn't the release's (#261) costs no attempt: an exception during the import moves the job back to SABnzbd's completed dir and leaves the album `grabbed`, so that recovery imports it again (`[RETRY]`; the third crash in a row counts against the release like a failed import), and a completed job whose dir is gone is searched again at the next top-up, ahead of the queue, without a blocklist entry (`[LOST]`). A pod replaced mid-import leaves the rest of the job in `inbox/usenet/<playlist>/`: at start the service moves it back to SABnzbd's completed dir before anything scans (`[RESUME]`, #344), so the recovery imports it as a retry, its items counted from the first try's start and judged on the first try's MusicBrainz match, instead of a scan importing it loose. MusicBrainz being down is not the release's fault either (#264): beets gives up on a request after its own retries (six, with a short backoff, not configurable), skips the track and exits 0, so the scan watches beets' output for `Max retries exceeded` on `musicbrainz.org`. When the import left inbox files behind, it then leaves them in the inbox instead of quarantining them, fails with `music_scan_last_failure_reason{reason="musicbrainz_unavailable"}`, and the album import retries the job the same way (`[RETRY] n/12`, about six hours of ticks) before the release takes the blame. An import that brought in every inbox file despite the errors (beets runs several searches per singleton, so one 503 rarely costs a match) only logs a warning: the scan succeeds and the release is claimed and judged at once (#286). `music-album-reset <artist or album>` (or the album's Spotify ID; an exact `artist — album` wins over the longer names that contain it, #289) undoes an album's last attempt by hand (back to `wanted`, its last release off the blocklist, one attempt fewer, its spotdl queue cleared); `--reimport` starts it over from one release instead (blocklist and attempts cleared, grabbed although the library has its tracks, the old copies retired on import); dry run unless `--apply`. `music-album-audit-releases` lists the imported albums the track-level rules before #279 mixed from several releases or topped up from spotdl (`[MIXED]`), each with its `--reimport` command. An album imported whole since #279 is never mixed, and local-only extras and a spotdl copy another playlist also lists don't count (#295): a reimport retires neither; `--replaced '<artist or album>'` lists that album's copies in `quarantine/replaced/` (by their album and artist tags): `[REPLACED]` when a library item holds the file's recording (its Spotify ID, ISRC or `mb_trackid` tags; an `mb_trackid` only from an item within 2s of the file's length, homelab#2540) or the file is a merge's loser whose keeper is still in the library and whose title and artist tags are the keeper's (#303, homelab#2539), `[ONLYCOPY]` when none does or the file has no identity tags. A file a keeper's `merged_files` names but whose title or artist isn't the keeper's (a wrong merge) is logged `[MISMERGED] <file>: <artist> — <title>, but merged onto <keeper id> (<artist> — <title>)` and judged by its identity tags alone. `--apply` deletes the superseded ones only; the only copies stay unless `--only-copies` is given too (#287). `--replaced` without a query lists every only copy in `quarantine/replaced/` (#298), read-only: under each album record that claims it (`[ALBUM] <artist> — <album> (<id>): N only copies`, with that album's `--replaced` command; a file two records claim is under both), then the files no record claims (`[UNCLAIMED]`: a `music-audit-dupes` merge's loser, `music-audit-lengths --replace`'s old audio), each with the item ID its name starts with, its tags and its identity tags. Its totals are the scan's `music_scan_replaced_files{kind}`; it refuses `--apply`, so delete album by album, and unclaimed files by hand. **The album tick does both by itself (#288).** In `on`, before its top-up, it resets mixed albums for a reimport, as `--reimport` does but keeping the blocklist (#305): a release that failed for the album before (another album, an incomplete copy, a broken download, or the track-level rules' `[FAIL]`) is not grabbed again, and a reimport that finds no other release keeps the album it has (`[STAYS]`; it stays mixed, for the operator), rather than going missing and to spotdl. The operator's `--reimport` still clears the whole blocklist, to start over when a blocklisted release is wanted after all. The top-up grabs the reset albums in the same tick: `ALBUM_AUTO_REIMPORTS_PER_DAY` in a rolling 24 hours (default 3, `0` turns it off), and only while the grab budget has room for the resets still waiting for their grab. Each reset logs `[AUTORESET] <artist> — <album> (<id>): <why it is mixed>; reimporting`. An album is reset automatically only once (`auto_reimported_at` on the album record); if it is still mixed after its reimport, `music-album-audit-releases` keeps listing it for the operator. Since an album imported whole is never mixed, a clean import, by hand or automatic, is not reset again. An album the operator holds is never reset: `music-overrides hold` (below). Every scan then deletes the files in `quarantine/replaced/` whose recording the library holds once they have sat there `REPLACED_RETENTION_DAYS` (default 14, from the move, the file's ctime; `0` turns it off), logging `[PURGE]`; an only copy is never deleted automatically. The `music_albums` push carries `music_albums_mixed` (imported albums still mixed, counted each tick) and `music_albums_auto_reimports_24h`; the `music_scan` push carries `music_scan_replaced_files{kind="superseded"|"only_copy"}` (what is left after the purge) and `music_scan_replaced_purged_total` (deleted by that scan). An original edition and its remaster on the playlists are two album records that can match the same release (#243): a release another record has in flight is not grabbed again (`[WAIT]`, searched again next tick), and one another record imported or keeps is skipped.

Searches use the names as release names spell them: diacritics folded, `$` as `s`, apostrophes deleted (`WHACK'S MUSEUM` searches and matches as `whacks museum`). A search with no results is retried once with the artist alone, which counts as a second indexer hit. A title made of glyphs is searched by the artist and matched on size alone (`[PICK] … (artist-only)`). An album whose artist and title are both glyphs is not searched; it logs `[NOWORDS] <album id>: … add a search override`. A search override gives an album its search words, which are both the query and what a release title must contain (`music-overrides search`, below). A missing album is searched again as soon as its query changes (a new override, or a normalisation fix). Spotify's bonus-track count (`Saint Cloud +3`) is dropped from the query and the match, like its bracketed edition notes (homelab#2568). `[MISS]` lines list the queries sent, so a miss can be checked in the indexer's own search, then why the results were rejected: how many failed each match rule (`album words`, `artist`, `reject word`, `leftover words`, `self-titled`, `single`, `size`, or `blocklisted` for one that fails none) and the three closest titles with the rule each failed, e.g. `rejected: 80 album words, 12 artist, 4 size; closest: "Artist-Album-CD-FLAC-1999-GRP" (size: 50 MB, not 70-4000 MB); …` (homelab#2568). A copy kept in the library is replaced only by its own edition, so its `[MISS]` may instead say `N match but not the edition of the copy kept (deluxe)`. An indexer in Prowlarr's failure backoff gets instant empty answers rather than errors, so the tick checks `/api/v1/indexerstatus` before its first search and after every empty result (#263): an indexer in backoff stops the tick with one `[ERR] … indexer in Prowlarr backoff` line, like a failed search, and the album keeps its status. As a guard against an indexer failing silently, 3 albums in a row with no results at all also stop the tick, and the third keeps its status.

A track spotdl's search can't find (`[MISS] … no source found`, e.g. a title made of glyphs) misses again on every retry, so it can be pinned to a source by hand (#247, `music-overrides pin`, below). A pin is a YouTube or YouTube Music video (an ID, or a `youtube.com`, `music.youtube.com` or `youtu.be` URL, reduced to its canonical watch URL, homelab#2411); another site or a playlist is refused, since the URL reaches yt-dlp. The nightly sync downloads a pinned track from that URL instead of searching (`[PIN] <track> → downloading from <url>`), ignores its backoff and spends the budget on it before the playlist's other tracks; the import and the scan's length guard treat it like any other download. A pin whose track the library already holds logs `[PIN] … already in the library; its pin is unused` and is skipped, so a stale pin can stay until it is tidied.

**Search overrides, holds and pins live in the music database** (homelab#2484, `music_fetch.overrides`), and the tick and the nightly read them on every run, so a change needs no restart. `music-overrides` lists and changes them, every write a dry run unless `--apply`, free text after `--`: `search [--reason=…] -- <album> <words…>`, `clear-search -- <album>`, `hold --reason=… -- <album>`, `release -- <album>`, `pin [--label=…] [--reason=…] -- <track> <https url>`, `unpin -- <track>`, and `list [--kind search|hold|pin]`. An album is anything that names its row: its key, any of its Spotify album IDs or URLs, its release group, or `artist — album`; a track is a Spotify track ID or URL. An override or hold is kept on the album's database row, not its release group, so it holds for an album with none yet, and it follows the row through a merge, or back to the album when an album that left its playlists returns (by its Spotify IDs, name or release group); one that clashes with the row's own stays detached, and `list` shows it. Each write records an `override_set` or `override_cleared` event with its caller in the same transaction; that, and each entry's `set_by`, `set_at` and reason, is the audit trail. The Music MCP's tools run the same command.

They were the homelab ConfigMap's `album-overrides.conf` and `track-pins.conf`. `music-overrides import` (dry run unless `--apply`) copies their entries in once, each with the comment block above it as its reason; an entry no album row has yet is imported detached and attaches when one does; entries held already are skipped. Until it has run (the `overrides-imported` kv marker) the pipeline reads the files, and after it ignores them.

**spotdl fallback (#205).** In `on`, what Usenet can't supply goes to spotdl: a `missing` album (from its first miss) or a `failed` one. An imported release never falls back, and sends nothing to spotdl (#268, #279). spotdl fetches the Spotify album's whole tracklist, not just the playlist's tracks: the tick reads it once per album (two Spotify calls, `album_songs` on the album record, up to 10 albums a tick), and until then the playlist's tracks stand in. The album becomes `fallback` (`[FALLBACK] … N track(s) left to spotdl (<why>)`), its absent tracks' Spotify IDs are kept in `fallback_tracks` under its first playlist, and album mode no longer searches it. A record from before #268 whose fallback came from an imported release (`fallback_from: partial` or `gap`) is settled by the next tick: `imported`, `settled_from` keeps why, the tracks spotdl already fetched stay and the rest leave its queue (`[SETTLED]`). The nightly sync downloads those tracks into the album playlist's inbox at the playlist's place in `playlists.conf` order, from the same `SYNC_TRACK_LIMIT` budget, with the usual `[HAVE]` check, backoff and length guard, and never rewrites the album playlist's store. Once the library holds every track of the album's tracklist the tick marks the album `filled` (`[FILLED]`). `music_albums{status="fallback"|"filled"}` and `music_albums_fallback_tracks` (tracks waiting) are on the `music_albums` push. `music-album-requeue [<album id>…] [--since <ISO time>]` puts albums a miss demoted (`fallback_from: missing`) back to `wanted`, by key or by when they fell back, and takes their tracks spotdl hasn't downloaded yet off its queue; dry run unless `--apply`. It is the recovery for misses that were really an indexer outage.

**Usenet first for spotdl playlists (#324).** Every spotdl playlist (no `album` or `nosync` flag) stays a spotdl playlist (nightly sync, track-level `.m3u`), but each album holding `ALBUM_WANT_MIN` (default 2; `0` turns this off) or more of its wanted tracks is grabbed whole from Usenet by album mode, and spotdl's nightly budget goes to the rest. At every album tick each playlist's want list (as the nightly computes it, backoff not applied) is grouped by album, and the threshold counts across playlists: one wanted track on each of two playlists is two (a track both list counts once). Each album at or over it becomes an album record with `origin: "wants"` holding each playlist's wanted tracks only, searched after the album playlists' records, most wanted first, then by its first wanted track (playlists in `playlists.conf` order, then position). Skipped, so their tracks stay on spotdl: albums with no Spotify album ID (local files), and an album an `album` playlist already wants whole (an album playlist that adds a wants record's album takes the record over). A wants record whose album falls under the threshold (its tracks removed on Spotify, or downloaded another way) is dropped while it is `wanted`, `dry-run`, `missing` or `have`. **The hold reaches only the next few grabs:** in `on`, a wants record's tracks are held off spotdl's want list while it is `grabbed`, or `wanted` and among the first records, in search order, that the next `ALBUM_MAX_IN_FLIGHT` × `ALBUM_WANT_HOLD_AHEAD` grabs (default 3 × 4; never more than `ALBUM_GRABS_PER_DAY`) reach after the album playlists' `wanted` records. SABnzbd's queue sets the pace, not the grab budget, so the rest of the queue stays on spotdl until its turn nears, so a long queue never starves the nightly; an album spotdl completes meanwhile drops out of the queue. The import is album mode's (the release is imported whole, other copies superseded), and the wanted tracks reach the playlist's `.m3u` at the next scan. Unlike an album playlist's record, a wanted track the release lacks goes back to spotdl, and a `missing` or `failed` record queues no whole-album fallback: its wanted tracks just return to the want list (a `missing` one is searched again after a week). The grab and indexer budgets are shared, album playlists first. Each tick logs `[WANTS] <playlist>: N album(s) queued (M wanted track(s)), K held off spotdl` (plus the skips), the `[GRAB]`/`[DONE]` lines name the playlist (`(wants: <playlist>)`), and the `music_albums` push carries `music_albums_status{status, origin}` (`origin` `album` or `wants`) beside `music_albums{status}`. `music-audit-want-albums` leaves the held tracks out, so it shows what is left for spotdl.

**Library-wide (homelab#2403).** `ALBUM_LIBRARY` (`off`, the default; `dry-run`; `on`) extends the rule to the whole library: an album is grabbed whole when `ALBUM_WANT_MIN` or more of its tracks are referenced, counting the library's items by `spotify_album_id` (one per recording, playlisted or not) and every store's wanted tracks (album and `nosync` playlists included), even when none of them is missing. Skipped: albums the library holds whole (Spotify's track count, or placed by a release import), local keys, albums an album playlist's or a wants record has (the wants feed runs first and takes a waiting library record over), and albums no store lists a track of (the import files an album under a playlist; `[LIBRARY] … no playlist track skipped`). Each becomes a record with `origin: "library"` whose `playlists` hold every store track on the album, held or wanted, so `have` and the import treat it as an album playlist's: it is `have` once the library holds it whole, and after the import supersede replaces the loose copies. It is searched after the album playlists' and the wants records, most referenced first, shares their budgets and their hold, and never falls back (a wanted track the release lacks stays with spotdl). A waiting library record whose album no longer qualifies is dropped. `dry-run` queues nothing and logs `[LIBRARY] dry-run: N album(s) would be queued (M new)` and the first ten; `on` logs `[LIBRARY] N album(s) queued (M new), K held off spotdl`; `off` (or `ALBUM_WANT_MIN=0`) drops the waiting library records. `music_albums_status` carries `origin="library"`. `music-audit-want-albums --library` is its baseline.

This file is the single source of truth for playlists. `music-ingest` reconciles disk state to match it on every run — provisioning new entries, reconciling the `.nosync` and `.album` sentinels, and deleting the playlist store and `.m3u` of a playlist removed from it. Navidrome imports each `.m3u` as a synced playlist and keeps it when the file goes, so the reconcile then sweeps Navidrome (homelab#2541, `music_scan.navidrome.sweep_playlists`): through Navidrome's native API (the Subsonic API's playlists carry no file path), it deletes each playlist whose file path is in Navidrome's view of `playlists/` (`NAVIDROME_PLAYLISTS_DIR`) and gone from the pipeline's, with sync on, logging `[NAVIDROME] deleted playlist <name>: imported from <path>, which is gone`. The match is by file path, never by name: a playlist made in Navidrome has no path and is never touched, even with a removed playlist's name. A playlist still in `playlists.conf` is left (its `.m3u` is due back), and so is one whose sync the operator turned off in Navidrome. A Navidrome failure is logged and doesn't fail the reconcile; every nightly sweeps, so the next one retries. Navidrome's scanner imports the playlists as its first admin, private, so `NAVIDROME_USER` must be a Navidrome admin to see and delete them (a warning says so when it isn't).

### 5. Run the first ingest

```bash
just fetch
```

This writes a playlist store for every entry in `playlists.conf` and begins downloading. To add or remove playlists later, just edit `playlists.conf` and run `just fetch` again.

### 6. Start the service

```bash
op run --env-file=.env.tpl -- docker compose up
```

This starts the Prefect server and the `music-pipeline` service. The fetch flow runs daily at 03:00 UTC by default — override with the `FETCH_CRON` env var. The scan flow runs automatically whenever new audio files arrive in the inbox.

To avoid rate limiting on large playlists, set `SYNC_TRACK_LIMIT` to cap total new downloads per session across all playlists. The pipeline resumes where it left off on the next run.

## Kubernetes deployment

This section contains everything an agent needs to write the k8s manifests.
The canonical manifests live in the homelab repo.

### Architecture

One long-running `Deployment` for the `music-pipeline` service, plus an optional `Deployment` for the Prefect server (for the UI and flow run history). Scheduling is handled internally by Prefect via the `FETCH_CRON` env var — no k8s CronJobs needed.

The Music MCP adapter ([`mcp/`](mcp/README.md), `ghcr.io/sometimeskind/music-mcp`) is a separate `Deployment` in its own namespace that talks to this service's `/mcp-api/*` only.

Without `PREFECT_API_URL` set, the service runs in direct mode: flows execute in-process and the Prefect server is not required. Use this for a simpler deployment with no UI.

### Typical k8s playlist workflow

Playlist management is fully declarative: edit `config/playlists.conf` and update the `music-pipeline-playlists` ConfigMap. The next fetch flow run reconciles disk state automatically.

**Add a new playlist:**
1. Add the entry to `config/playlists.conf`, commit and push.
2. Update the `music-pipeline-playlists` ConfigMap (or let GitOps do it).
3. The next scheduled fetch run writes its playlist store and begins syncing.

**Freeze a playlist (stop syncing):**
1. Add `nosync` as the third field on the playlist's line in `config/playlists.conf`.
2. Update the `music-pipeline-playlists` ConfigMap.
3. The next fetch run creates the `.nosync` sentinel automatically. A playlist frozen before its first sync is read from Spotify once and then downloads its missing tracks over the following nights.

**Remove a playlist:**
1. Remove the entry from `config/playlists.conf`, commit and push.
2. Update the `music-pipeline-playlists` ConfigMap.
3. The next fetch run deletes its playlist store, `.m3u` and inbox dir. Its tracks stay in the library, and their `sources` still name it (where they came from).

**Trigger a manual fetch now:**
```bash
kubectl exec -n <ns> deploy/music-pipeline -- \
  curl -s -X POST http://localhost:8080/fetch/trigger \
    -H "Authorization: Bearer <token>"
```

**Backfill track identity (once, #176):** items imported before Spotify IDs and ISRCs were stored get them from the playlists' Spotify pages (about one call per 100 tracks). It also lists **wrong versions**: playlist entries an older artist+title duplicate check merged into a different recording (live, remaster, radio edit). A candidate whose ISRC MusicBrainz lists on the item's recording (`mb_trackid`) is the same recording under another ISRC, not a wrong version (`[SAME]`); only those candidates are looked up, at one MusicBrainz call a second.
```bash
kubectl exec -n <ns> deploy/music-pipeline -- music-backfill-ids                            # dry run: report only
kubectl exec -n <ns> deploy/music-pipeline -- music-backfill-ids --apply                    # write IDs and ISRCs
kubectl exec -n <ns> deploy/music-pipeline -- music-backfill-ids --apply --redownload 10    # also fetch 10 right versions
```

**Audit and replace wrong audio (#165):** the length guard only checks new downloads. `music-audit-lengths` reads every playlist (`nosync` and `album` ones too) from its Spotify pages (about one call per 100 tracks) and lists `[SUSPECT]` items whose length is off from the Spotify entry's by more than 10% and 5s, with the YouTube video spotdl downloaded them from. `--replace` re-downloads one item, pinned to a YouTube video, and swaps the file **in place**: the item keeps its id, tags, playlists and IDs, and the old file goes to `quarantine/replaced/`. Going through the inbox doesn't work, since the duplicate hook would merge the new file into the old item by Spotify ID and drop it.
```bash
kubectl exec -n <ns> deploy/music-pipeline -- music-audit-lengths                         # report suspects
kubectl exec -n <ns> deploy/music-pipeline -- music-audit-lengths --silence --quarantine  # also mid-track silence; guard over quarantine
kubectl exec -n <ns> deploy/music-pipeline -- music-audit-lengths --replace <id> --youtube <url>          # dry run
kubectl exec -n <ns> deploy/music-pipeline -- music-audit-lengths --replace <id> --youtube <url> --apply  # replace
```
Without `--youtube` spotdl searches again and usually picks the same video; the replace then stops. A download that fails the guard is refused unless `--force`.
`--redownload` downloads into the playlist's inbox (works for `nosync` and `album` playlists too) and takes the playlist off the wrong item; the next scan imports the download as its own recording.

**Duplicates (#210):** `music-audit-dupes` finds duplicates already in the library, in two tiers. **Certain:** a shared Spotify ID or ISRC, a shared MusicBrainz recording ID with lengths within 2s (homelab#2540: beets imports singletons and names each file's recording by a best guess, so a 5.1 mix or a live take can share a stereo or studio track's ID at another length), or an AcoustID match (shared `acoustid_id`, or fingerprints compared between items that share an artist word) with lengths within 2s and the same title once edition suffixes are dropped. **Uncertain:** title+artist only (the album matcher's normalisation), or an AcoustID match or shared recording ID with lengths further apart, or between different titles (likely a wrong download: fix it with `--replace` above, never a merge); listed, never merged by `--apply`, since a demo or live take must stay its own item. Title+artist pairs with disjoint ISRCs are the duplicate hook's `[SPLIT]` decision and are only counted. On album playlists the album is the unit (#279), so a certain group whose items sit on different album records (a greatest-hits and the studio album), or that holds two tracks of one album record (a deluxe listing a recording twice: two release items, or two local-only extras and no release item), is not merged by `--apply` (#311): it is listed `[ALBUM]` with the reason and a `--merge` command per pair, for the operator. An extra and its own record's release item are one album's copies and merge. `--apply` merges each other certain group onto an album record's release item, else one of its extras, so the album keeps its track; then the item whose length is closest to Spotify's (then bitrate, playlists, the older item): it takes the others' `spotify_ids`, `isrc`, `sources` and a missing `mb_trackid`, their files move to `quarantine/replaced/` (never deleted), the `.m3u` files are regenerated, then Navidrome rescans. The keeper records the moved files' names in its `merged_files` flex attribute (`/`-separated, passed on when it is merged in turn), so they count as superseded and the purge deletes them while it is in the library, whatever the loser's own identity tags (none, or an `mb_trackid` the keeper lacks, #303). A name is not an ID, though: a wrong merge leaves its loser's name there (unlinking the wrong Spotify ID doesn't take it out, and a later merge carries it on), so a file counts this way only while its title (edition notes dropped) is the keeper's and their artists share a word when both are known (homelab#2539). Otherwise, and for an untitled or unreadable file, only its identity tags count, and with none held it is an only copy and stays; `music-album-audit-releases --replaced` logs it `[MISMERGED]`. Once the keeper leaves the library they are only copies again. The keeper isn't moved; run `music-canon-albums` afterwards to file it under its album. **`--merge <keep> <drop>...` merges a pair you have confirmed (#276)**, usually from the uncertain tier, which prints the command for each of its pairs (`if one recording: music-audit-dupes --merge 2898 92`, keeper by the same rule; a group of three prints one per pair, so copy only the pairs that are one recording; a pair two rules found prints once). It goes through the same merge as `--apply` (the keeper takes the drops' IDs, playlists and a missing `mb_trackid`, their files go to `quarantine/replaced/`, the `.m3u` files are regenerated and Navidrome rescans), under the pipeline lock. Without `--apply` it prints the keep/drop block and what moves. It refuses unknown IDs, the keeper among the drops, and a manually imported drop (any `via` but spotdl/usenet) unless `--allow-manual`. A drop that is a track of an album record merges too, with a warning (`[ALBUM] <id> is a release item of album record <id> [<album>]: its album loses the track`), unless it is an extra merged into its own record's release item. **`--unlink <id> <spotify track id>` takes one Spotify ID off one item (homelab#2530).** A playlist entry resolves by Spotify ID before ISRC, so an item that wrongly holds an entry's ID (a wrong merge brought it along: its `merged_files` names the entry's song) takes the slot even when the right item is in the library and holds the entry's ISRC. Without `--apply` it prints the item's `spotify_ids` before and after and, for each playlist entry with the ID, the item it resolves to afterwards (the lowest item holding the ID, else the ISRC) or that the slot goes empty. With `--apply` it stores the item, records a `wrong_version` event, regenerates the `.m3u` files and rescans Navidrome, under the pipeline lock. It refuses an ID the item doesn't hold, and the item's `spotify_url` ID (the file was downloaded for that entry: a wrong download is `--replace`d, not unlinked). Undo it with `beet modify id:<id> spotify_ids=<before>`. Each audit pushes `music_dupes_groups{tier}` (Pushgateway job `music_audit_dupes`; the `[ALBUM]` groups count as uncertain). `chroma` fingerprints only autotagged imports, so asis imports had none; the plugin now fingerprints them at import, and `music-audit-lengths --replace` refingerprints the new audio. For the items already in the library, `--fingerprint --apply` stores one for each item without (database only, files untouched), so run it first; `--fingerprint <id>...` recomputes items replaced before this, which still carry the old audio's fingerprint.
```bash
kubectl exec -n <ns> deploy/music-pipeline -- music-audit-dupes --fingerprint           # count items without a fingerprint
kubectl exec -n <ns> deploy/music-pipeline -- music-audit-dupes --fingerprint --apply   # fingerprint and store them
kubectl exec -n <ns> deploy/music-pipeline -- music-audit-dupes --fingerprint 873 615 --apply  # refingerprint these items
kubectl exec -n <ns> deploy/music-pipeline -- music-audit-dupes                         # dry run: both tiers with evidence
kubectl exec -n <ns> deploy/music-pipeline -- music-audit-dupes --apply                 # merge the certain tier
kubectl exec -n <ns> deploy/music-pipeline -- music-audit-dupes --merge 2898 92         # dry run: merge 92 onto 2898
kubectl exec -n <ns> deploy/music-pipeline -- music-audit-dupes --merge 2898 92 --apply # merge it
kubectl exec -n <ns> deploy/music-pipeline -- music-audit-dupes --unlink 9674 2o49Twc3qrNMOt8gq9W06L          # dry run: take that ID off 9674
kubectl exec -n <ns> deploy/music-pipeline -- music-audit-dupes --unlink 9674 2o49Twc3qrNMOt8gq9W06L --apply  # do it
```

**Guessed recording IDs (homelab#2543):** beets imports every file as a singleton and names its recording (`mb_trackid`) by a guess from title, artist and length, so a sibling recording can win: a 5.1 mix for a stereo track, a live take for a studio one, an alternate version. `music-mb-fingerprint --recheck` checks each item that has an `mb_trackid` against its own audio: it looks the file up on AcoustID (no MusicBrainz calls; pyacoustid keeps to AcoustID's 3 requests a second, so the whole library takes hours) and reports `[RECHECK] <id> — <title>: mb_trackid <guess> is not among its AcoustID recordings (<top> <score>): …` when the guess isn't among the recordings AcoustID links to the fingerprint at 0.85 or more. With exactly one such recording the line ends `→ <recording>`, and `--apply` replaces the guess with it. With several, none is chosen and the item is left alone. AcoustID having nothing at 0.85 is `[NOMATCH]`, left alone too (some releases are unknown to it). A request fallback's item (`fallback_recording`, which AcoustID already named) is skipped. A merge or supersede keeper (`merged_files`) is checked and replaced like any item, and marked `(a merge keeper)`: a merge joins only copies with the same audio or a shared ID, so the ID it carries from a loser is that loser's guess, and its losers' files stay superseded by `merged_files` (while their title and artist are the keeper's, homelab#2539). A `[SUMMARY]` line gives the counts checked, agreeing, flagged (replaceable, with several recordings, merge keepers among them), no match, errors, gone and skipped, and with `--apply` the count replaced. Item IDs after the flags limit the run to those items. `[PROGRESS] <n>/<total>, <x> flagged so far` every 500 items says how far a whole-library run has got. The lookups run without a lock, so the pipeline's ticks go on during the run and may move, retire or purge a file: each item is re-read from the library just before its lookup, and one gone from the library, or whose file went away between the read and the fingerprint, is logged `[GONE]`, counted in the summary and not checked (re-run with its ID). Start a whole-library run just after an album tick, so the fewest files move under it. `--apply` then takes the pipeline lock and, item by item, skips one whose `mb_trackid` changed meanwhile, and stores the new ID with a `recording_replaced` event (migration 11; `data.old`, `data.new`, `data.score`) in the same transaction. It refuses to run without `MUSIC_DATABASE_URL`. Then it writes the file's tags. `mb_releasetrackid` and the title are left as they were. Navidrome identifies a track by its `mb_trackid`, so a replaced item may show as a new track there, without its play count and stars (accepted by the operator, 2026-10-31). Undo one with `beet modify id:<id> mb_trackid=<old>` (the event's `data.old`). Without `--recheck`, `music-mb-fingerprint` still only fills a missing `mb_trackid`.

```bash
kubectl exec -n <ns> deploy/music-pipeline -- music-mb-fingerprint --recheck 6994 5672    # dry run: these items
kubectl exec -n <ns> deploy/music-pipeline -- music-mb-fingerprint --recheck              # dry run: the whole library
kubectl exec -n <ns> deploy/music-pipeline -- music-mb-fingerprint --recheck --apply      # replace the flagged guesses
kubectl exec -n <ns> deploy/music-pipeline -- music-mb-fingerprint --recheck --run-id r1  # a recorded dry run; the same command continues it
kubectl exec -n <ns> deploy/music-pipeline -- music-mb-fingerprint --replace-run r1       # what applying run r1 would do now
kubectl exec -n <ns> deploy/music-pipeline -- music-mb-fingerprint --replace-run r1 --apply
```

**A recorded recheck (homelab#2553):** a whole-library run takes about an hour, so `--recheck --run-id <id>` records it in the music database (migration 12): a `long_runs` row with its checkpoint (items walked, the last item ID, the counts so far) every 25 items, and its findings in `recheck_findings` (each flagged item's guess, its recordings, the one replacement if there is one, and its file's path, size and mtime at the lookup). It walks the items in ID order. Started again with the same ID (and the same item IDs, if any), it continues after its checkpoint with `[RESUME] run <id>: continuing after item N (P of T walked, F flagged so far)`, so a killed run loses at most 25 lookups. A run that stopped on failed lookups is `failed` and continues the same way; a finished one is never re-run (start a new ID). One process at a time holds a run (a Postgres advisory lock); a second is refused. A recorded run is always a dry run. `--replace-run <id>` reads its findings, never AcoustID, and lists for each replaceable item what an apply does as the library stands now: `[WOULD-REPLACE]`, `[SKIP] <id>: <why>` (gone, its `mb_trackid` changed, or its file changed since the check: `replace_item` swaps the audio and keeps `mb_trackid`, so the ID alone can't tell; recheck such an item by ID), or `[DONE]` (it holds the replacement already). `--replace-run <id> --apply` does it under the pipeline lock, each replacement with its `recording_replaced` event (`data.run` names the run) and the finding's outcome in one transaction. An interrupted apply is finished by running it again: every item is checked again, and one that holds its replacement already has its tags written again (and its event recorded, if the kill came before it). The apply refuses a run that isn't finished or finished more than 7 days ago; the nightly prunes runs 30 days after they finish. The plain `--recheck` (no run ID) is as before, except that its `--apply` also skips an item whose file changed since its lookup.

**Titles of the wrong version (homelab#2544):** beets' singleton match writes the closest MusicBrainz recording's `title` and `trackdisambig` over the file's, and the closest can be a sibling: a stereo album track titled *(5.1 mix)*, a studio track with `trackdisambig` "live, 1992‐05‐28: …". `music-audit-titles` lists the items whose `title` or `trackdisambig` names a version (`5.1`, `live`, `demo`, `alternate` (also `alt`, `alternative`), `mono`, `take`, `outtake`; whole words, any case) that Spotify's entry at the item's slot doesn't: the playlist-store record for one of its Spotify IDs, the one on its `spotify_album_id` first, else canon's preference. A word in the title counts when it appears more often than in Spotify's title, so a song whose name holds it (*Live Forever*, *Take Five*) is not flagged; a word in `trackdisambig` counts when Spotify's version part (after ` - ` or in brackets) lacks it. Words only Spotify's title names are never flagged, and a word in Spotify's album name counts as Spotify's (a live album's tracks are often titled bare). Grouped by album (sorted by album, then disc and track), each `[VERSION]` line gives the item ID, its position, our title and `trackdisambig`, Spotify's title and the differing words, and each album with a record its `music-album-reset … --reimport` command: the fix is the album's. Items with no Spotify ID, or whose IDs no store describes, are counted, not compared. It can't see a wrong title with no version word in it (a different song under the slot's version notes), and a song whose name holds a version word only on our side (Spotify spelling it otherwise) shows as a false positive. Read-only: the library and the stores, no Spotify or MusicBrainz call. The Music MCP runs it as `audit_titles`.
```bash
kubectl exec -n <ns> deploy/music-pipeline -- music-audit-titles
```

**The want list by album (#322, homelab#2362):** `music-audit-want-albums` shows how far whole-album Usenet grabs would get a spotdl playlist before it switches to Usenet first. For each spotdl playlist (every store without an `.album` or `.nosync` sentinel; `--playlist <name>` for one, `--all` for every store) it takes the want list as the nightly computes it (entries no library item holds by Spotify ID or ISRC, minus downloads held in the inbox or quarantine; backoff is not applied) and groups it by album: one `[WANT]` summary per playlist (wanted entries, albums they span, albums with at least `--min` wanted tracks, default 2, and the wanted tracks those cover, singletons), the albums at or over the threshold most wanted first (`[ALBUM] <playlist>: N of M track(s) wanted, first at #<position>: <artist> — <album> (<Spotify album id>)`), then the total across playlists, counted as the album tick's wants feed counts them (homelab#2406): the albums merged by album key (two Spotify editions the album store has as one record count as one album), each wanted track once however many playlists list it, and `--min` applied to the merged albums, so an album with one wanted track on each of two playlists holds 2. Its entries are the playlists' summed (they are playlist slots). With `--all` the total spans album and `nosync` playlists too, which the feed doesn't; run without it for the feed's playlists. Unlike the feed, it leaves out the tracks album mode already holds, so it shows what is left for spotdl. Read-only, and no Spotify or indexer call. A big playlist can be measured before any download by registering it as `nosync` first (its store is built from one Spotify fetch) and running `--playlist <name>`. `--library` (homelab#2403) is the baseline for a library-wide rule: every library item by its `spotify_album_id` (one per recording; items with none are counted and left out) plus every store's wanted tracks (nothing held back), the albums that reach `--min` sorted into `whole` (Spotify's track count held, or a release import placed it), `album playlist`, `queued` (a wants record), `grab` (a track wanted) and `backfill` (nothing wanted), then what grabbing the last two whole would land (tracks, GB at the library's mean file size) and how many loose copies supersede would replace, and each such album (`[GRAB]`/`[BACKFILL] N held + M wanted of T: <artist> — <album> (<id>)`).

```bash
kubectl exec -n <ns> deploy/music-pipeline -- music-audit-want-albums                       # every spotdl playlist, albums with 2+ wanted
kubectl exec -n <ns> deploy/music-pipeline -- music-audit-want-albums --playlist big --min 3  # one playlist, albums with 3+ wanted
kubectl exec -n <ns> deploy/music-pipeline -- music-audit-want-albums --library              # library-wide baseline, held + wanted
```

**Failed releases imported before #238:** `music-rollback-releases` lists the `via=usenet` items that match no playlist entry and came from a failed release, and with `--apply` quarantines them like the rollback above. Each item is attributed to an album record in the album store by album name (edition suffixes dropped) and artist: it came with the successful release when it was added between the record's last grab and its import (a full or partial import), otherwise from a failed one. Items no record claims are listed as `[UNKNOWN]` and kept, and a successful release's extras as `[KEPT]`. A failed release's item that is one of its album's tracks the library still lacks (same title, artist within a `feat.` credit, #240) is listed as `[LINK] … → <spotify id>` and gets that ID instead of being quarantined. With `--apply` a linked item is canonicalised right away (#244); the scan also picks up any item that got a Spotify ID after its import.

```sh
kubectl exec -n <ns> deploy/music-pipeline -- music-rollback-releases          # dry run: [LINK], [FAILED], [KEPT], [UNKNOWN]
kubectl exec -n <ns> deploy/music-pipeline -- music-rollback-releases --apply  # link [LINK], quarantine [FAILED]
```

**Album covers (#204):** Usenet album tracks get Spotify's album cover embedded after import (the convert command drops a FLAC's picture, and singleton imports get no `fetchart`/`embedart`). The cover URL comes from the playlist stores, so no Spotify calls. `music-embed-covers` backfills every `via=usenet` item with no embedded art, then triggers a Navidrome rescan:
```bash
kubectl exec -n <ns> deploy/music-pipeline -- music-embed-covers           # dry run: [ART] line per album
kubectl exec -n <ns> deploy/music-pipeline -- music-embed-covers --apply   # embed, then rescan Navidrome
```

**Canonical albums (#209):** Spotify decides album grouping. An item with a Spotify ID takes `album`, `albumartist`, the release date and its track/disc numbering from the Spotify album its playlist entry is on (an `album` release over a `single` or `compilation`, then one a playlist names today, then the earliest), and beets moves the file. A track on a `single` moves to a standard album by the same album artist holding the same recording (an EP, which Spotify files as `single`, only when the track is already filed under it), found by ISRC with a Spotify track search (cached in the `canon-isrc` document, one search a second, 20 per scan; a track still waiting for its search is marked `canon_wait` and picked up by the next scan). Its cover follows when the album name or album artist changes, or when the file has none. An item whose move would land on another file's path is left as it is (`[CLASH]`, a duplicate for #210); an album record's item is tagged in place instead (#306). Spotify sometimes lists one album twice (#214): releases of the same type with the same album artist and name form a twin group whose representative (most playlist entries, then the earliest, then the most tracks) takes every item once its recording is known to be on it, by a playlist entry's ISRC or the same ISRC search (`[TWIN]` lines in the dry run; `[NOTWIN]` when the search shows the recording only on the other release, as for two self-titled albums). A change to beets-only fields (`spotify_album_id`, `mb_album_via`) updates the database without rewriting the file. Navidrome groups by the MusicBrainz album ID first, so the album-level MusicBrainz tags follow too: the release MusicBrainz links to the Spotify album URL, else one holding the album's ISRCs with its track count and title, else one with its barcode (one Spotify album call), else they are cleared (`[MB-NONE]`, with a Harmony link to add the release to MusicBrainz). Track-level IDs and ISRCs stay. Lookups are cached in the `mb-releases` document; each scan resolves up to 20 albums and leaves the rest `mb_album_via=pending` for the next, and misses are retried weekly. A Usenet release is the album (#266, #279): an item stamped `album_record` takes its record's Spotify album (album, album artist, date, cover, `spotify_album_id`) and the MusicBrainz album tags of the release its files are (`mb_album_via=files`), and keeps the release's own disc/track, whatever its Spotify track IDs say or whether it has any; a `.album` playlist lists those items alone, in disc/track order. Older release items keep #278's rule: on their album record's album when one of their IDs is (`[HOME]`). Album tracks get Spotify IDs only from ISRC or disc/track, never by matching an item's title to an entry. **The album copy supersedes loose copies that predate it** (`music_scan.supersede`): a non-Usenet item with the same Spotify ID, ISRC or MusicBrainz recording ID as one of the release's items, or at the slot of a release item with no Spotify ID on the same Spotify album when the release has Spotify's track count, is merged into the album item (`[SUPERSEDE]`). A loose item canon moved onto the album from a twin release holds the twin's Spotify ID, so the album's tracklist resolves it (#274): the entry with its ISRC, else the entry at its disc/track (vetoed by disjoint ISRCs), and the album item holding that entry's Spotify ID replaces it. The album item takes its playlists, IDs and `mb_trackid` (so Navidrome keeps plays and stars), its file goes to `quarantine/replaced/`, the album item moves to the freed path when it sat beside it as a `.1` copy (`[MOVE]`), and the `.m3u` files are regenerated. A Spotify ID from the title rung never supersedes. A loose item on the album that matches nothing is kept and listed as `[KEEP]` with the reason (no Spotify ID, no tracklist, its track held by no release item or only by title words, no entry at its slot, disjoint ISRCs) for `music-audit-dupes`; a manual import is never replaced (`[MANUAL]`). The duplicate hook imports a Usenet track whose same-recording duplicates are all spotdl items (`[ALBUM]`) so that the supersede can run. Runs at every scan and after each Usenet album import (supersede after every import). `music-canon-albums` backfills, supersedes included, the library from the playlist pages (cached for a day, so the `--apply` after a dry run reads Spotify once):
```bash
kubectl exec -n <ns> deploy/music-pipeline -- music-canon-albums           # dry run: [ALBUM]/[RETAG] lines and totals
kubectl exec -n <ns> deploy/music-pipeline -- music-canon-albums --apply   # retag, move, regenerate the .m3u files (#218), then rescan Navidrome
```
The dry run still looks albums up on MusicBrainz (about 1–6 s each) and caches the results. `--mb-budget N` caps the lookups per run. The dry run also runs the single → album ISRC searches (one a second, cached for the `--apply`); `--search-budget N` caps them.

**Recover after PVC loss:**
1. Restore `beets-data` PVC from backup (restores `library.db`).
2. The state (album store, playlist stores, backoff, caches) is in the `music` database, which the PVC doesn't hold: restore it from its own backup only if the database was lost too. A fetch rebuilds every playlist store from Spotify and downloads only what the restored library lacks; local-only entries (none so far) are lost with the stores.

## Notes and gotchas

- **Track identity.** `spotify_ids` (comma-separated Spotify track IDs: one recording has different IDs on the single, the album and compilations) and `isrc` (`;`-separated, MusicBrainz's plus Spotify's) decide whether a playlist entry is a library item: Spotify ID, then ISRC, then MusicBrainz recording ID, and title+artist only as a logged last resort (`[WORDS]`, whole titles: a remaster is another track, #252). The title+artist resort only reaches items with no Spotify ID (#257): an item that has one is that track, so a same-title entry with another ID never takes it (the slots, `.m3u` regen, and a removal's title fallback alike). Two recordings are one track only when one of those identifiers agrees (#255): the duplicate hook merges an incoming track only on a shared Spotify ID, ISRC or recording ID (`[SAME]`; a recording ID only with lengths within 2s, homelab#2540), and a same-title track imports as its own item, `[SPLIT]` when the ISRCs differ and `[APART]` when one side has none. Real duplicates that arrive without IDs are found by `music-audit-dupes` (fingerprints).
- **`sources` is provenance, not membership.** A track imported or linked by several playlists carries all their names (e.g. `sources=playlist-a,playlist-b`), and keeps them after it leaves a playlist. What a playlist lists is its store's alone (homelab#1914).
- **Playlist slots (#228).** Each playlist entry is a slot that every scan fills by resolving it against the whole library by Spotify ID, then ISRC (`[SLOT] <playlist>: N entr(ies) filled from the library by ID/ISRC`, per track at debug), never by recording anything. So a track that arrived by any route (a Usenet album, another playlist's download, a manual import or replacement) is listed by every playlist that names it at the next scan, with no download and no tag write. The album hooks' `missing` and `have` read the same resolution. The scan pushes `music_playlist_slots_empty{playlist}` (entries with no item: on a spotdl playlist, tracks still waiting for a download).
- **`beet update` does not prune deleted files.** Use `beet remove <query>` with a specific query. Never run `beet remove` without a query.
- **Cookies expire.** Re-export from browser when downloads fail at quality.
- **Spotify rate limits.** Always use your own app credentials — the spotdl defaults are shared and hit limits quickly. For large playlists, set `SYNC_TRACK_LIMIT` to cap new downloads per session (e.g. `50`); the pipeline picks up where it left off each run. The budget is spent on one want list across playlists in `playlists.conf` order (new entries the library lacks, minus backoff); once spent, the remaining playlists are still fetched, `[HAVE]`-linked and diffed for removals, and only their downloads wait (counted in the `Track budget` line), so no playlist goes unchecked (#228).
- **Long Spotify rate limits fail the run.** A 429 whose `Retry-After` exceeds 120s is not slept through (it once said 17.5h): the run fails with `Spotify rate-limited: Retry-After <n>s, until <UTC>`, the end goes to the `spotify-rate-limit` document in the `music` database and to the `music_spotify_rate_limited_until_seconds` gauge (Pushgateway job `music_spotify`), and every Spotify reader fails without calling Spotify until then. Shorter ones are waited out.
- **MusicBrainz threshold.** `strong_rec_thresh: 0.10` in `config/beets/config.yaml`. Tracks that don't match confidently land in quarantine. A second `--asis` pass then imports any quarantined file that already has sufficient embedded tags (title, artist, album, tracknumber); the rest stay in quarantine for manual review. Raise the threshold if too many valid tracks are being quarantined.
- **The playlist store (homelab#1914) is the playlist state.** One row per playlist in the `music` database's `playlist_stores` ([State](#state)), holding every entry in Spotify's order with the full song record, then its local entries (library items on the playlist that are not on Spotify; none so far). "Downloaded" is the entry resolving to a library item by Spotify ID or ISRC, never recorded. The nightly rewrites a spotdl playlist's store from Spotify and downloads its want list: entries no library item holds, minus downloads waiting in the inbox or quarantine (never fetched again, #165) and backoff. The sync logs one summary line per playlist (tracks on Spotify, held or waiting, wanted split into on-the-playlist-before and new, removed) and one `[BACK]` count; only a track acted on (`[OK]`, `[MISS]`, `[FAIL]`, `[HAVE]`, `[PIN]`) gets its own line (#320). The album tick writes an `album` playlist's; a `nosync` playlist's is built from Spotify once and kept. A track removed on Spotify leaves the store and the `.m3u`; its file stays in the library (soft delete). Whether a spotdl copy is an album's top-up is the store's answer too (`release._topup`). The stores replaced `.spotdl`, the unlink queue and `reconcile` (stage c); old `.spotdl` files left on the PVC are no longer read.
